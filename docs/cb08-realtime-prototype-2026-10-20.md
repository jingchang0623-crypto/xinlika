**同一文件持续约 3 小时 20 分钟，没有发生三小时切段；重连后恢复同一录音的后续实时内容，但断连期间没有自动补发。** 因而“所有模式单文件最多三小时”不能作为本机已确认规格。本次不能推导独立按键录音、其他固件或全天电池续航，也未测到跨文件切段衔接。

### 三小时附近的逐帧核对

按卡上编码位置检查 10,790–10,810 秒（2:59:50–3:00:10），共 250 条业务帧、40,000B，覆盖该 20 秒全部内容；这些字节属于重连后整段唯一匹配的一部分，没有额外缺口或重复。窗口内相邻帧最大到达间隔约 0.120620 秒，逐帧位置和到达时间留在本机，文件哈希及首尾帧写入脱敏 JSON。

### 实验控制与下载修复

全程使用 `caffeinate -i`，设备处于充电状态，没有静音裁剪、低功耗切换或校时；第 30 秒主动断开一次，后续持续观察。只在当前身份仍为本次原始测试文件时发送保存命令；保存确认成功，没有删除录音。

初次参考下载停在 830,240B、没有结束码，拒绝作为完整参考。后续暴露断连时内存进度丢失，只在验证命令内补充恢复：字节写入私有文件，每次重连重查完整目录、同名/大小/计数及空闲状态，重读最多 160B 重叠并逐字节核对后追加。身份变化、重叠不符、越界、磁盘失败或重试无进展不能报成功；不裁剪残包。最终长测参考完整下载一次通过；另外一条历史参考实际经历 4 次恢复并完整通过。构建、48/48 原型逻辑自测、7/7 分析回归与 2/2 离线取样回归通过。

## 4. 硬件究竟有没有声音检测

当前结论：**没有找到本机型可核对的硬件 VAD/VOX/VOS 开关、检测阈值、检测事件或静音抑制协议。不能断言芯片不支持，也不能承诺当前固件支持。**

声云 SDK 明确暴露了 `getDeviceLowPowerRecordMode` / `setDeviceLowPowerRecordMode`，文档解释为长续航低功耗录音，返回 `low_power_state`。它没有说明是否依赖声音触发、降低采样率/算力、关闭无线或采用其他策略。SDK 返回 JSON 中的 cmd=22/23 是上层事件编号，不能把它们直接当成 BLE TYPE/CMD 发送。原型没有猜测私有命令或启用该模式。

本次能量分析中，按 -50dBFS 的实验阈值，有约 36.72 秒被标为低能量候选，期间仍收到固定格式音频。这说明当前观察到的工作模式没有抑制这些低能量时段的传输；它不是受控房间静音测试，也不证明所有场景下都没有硬件声控。

长测的 11,995.68 秒实时解码内容中，按同一阈值累计有 10,024.76 秒低能量候选，仍持续收到固定格式数据。该结果同样只描述当前模式的传输，不将低能量等同于无人说话，不从能量统计推导固件支持或不支持 VAD。

| 检测所在位置 | 能减少什么 | 不能直接减少什么 |
|---|---|---|
| 服务端 VAD | ASR/大模型处理，部分存储 | 设备录音、BLE、手机向服务端传输 |
| 手机端解码后 VAD | 云端上传、ASR 与模型开销，可只上传语音段及时间标记 | 已经发生的卡上录音和设备到手机的蓝牙传输 |
| 固件侧低功耗检测与唤醒 | 有机会减少卡上写入、编码和 BLE 发包 | 必须有低功耗监听维持检测；完全关掉拾音后无法知道声音何时回来 |

原型先完整保存音频以测量连续性。产品路径建议随后增加手机端语音检测、起点前缓存与结束后缓冲：例如先以 0.5–1 秒前缓存、约 1 秒结束缓冲做实验，避免切掉开头短词和尾音。这些是初始实验参数，不是已经标定的默认值。能量阈值只能筛出低能量候选，不能区分人声、风声、电视或用户本人；更不能在 BLE 没有数据时直接认定周围安静。

如果希望设备本身做到“没声音不录、不发”，应向硬件方确认本批次芯片/固件的：

- VAD/VOX/VOS 是否存在，是否可设置阈值、保持时间和前缓存。
- 低功耗模式的具体行为，能否同时实时推流。
- 静音时卡上是保存空白、跳过时间还是生成新段；是否提供采样时钟/时间标记。
- 恢复声音时由什么唤醒、是否会丢开头，是否发检测开始/结束和健康心跳。
- 重连能否按音频游标回放缺口，是否需要升级固件。

只有停止 BLE 推送、却没有低功耗检测事件与时间信息，会使手机难以分辨“安静”与“设备断流”，并压缩掉真实时间轴。需要把声音门控和采集健康一起设计。

## 5. 原型运行方式

```bash
swift build --product cb08-probe
.build/debug/cb08-probe scan --seconds 8
```

先从扫描结果取得目标 UUID。只观察已经在录的设备：

```bash
.build/debug/cb08-probe capture --device UUID --seconds 90
```

建立专用短测试并保留卡上文件：

```bash
.build/debug/cb08-probe capture --device UUID --seconds 70 \
  --start-if-idle --disconnect-at 15 --stop-owned-at-end \
  --output .build/cb08-captures/新的短测目录
```

默认重连只订阅观察。`--recovery resume` 或 `--recovery start` 是显式的单次实验分支：只在被动观察无音频、原型确实创建了该文件且新鲜身份/状态检查仍匹配时发送；不是日常重连策略。`start` 可能改变文件或计数，因此必须按实验结果判断，不以收到音频作为成功。

卡上停止录音后，下载已明确归属的测试文件作参考：

```bash
.build/debug/cb08-probe reference --device UUID \
  --filename noteYYYYMMDD-HHMMSS.opus \
  --output .build/cb08-captures/新的参考目录
```

观察状态和完成后的解码分析：

```bash
python3 scripts/cb08-probe-status.py .build/cb08-captures/某次采集
python3 scripts/analyze-cb08-capture.py .build/cb08-captures/某次采集 \
  --decode-cb08-40 --card-raw .build/cb08-captures/参考目录/测试文件.opus
```

分析工具使用 Python 标准库和 ffmpeg，不安装模型、不上传。`--decode-cb08-40` 显式采用厂商基线；非 40B 整数倍会报告失败，不裁掉残包伪造可解码结果。默认阈值 -50dBFS 只输出候选低能量窗口，不删除音频。重复静音导致参考匹配不唯一时会标为 ambiguous，不能用作唯一定位。

## 6. 实现和验证边界

新增独立 SwiftPM 原型及支持层；共享 BLE 层提供可选的帧观察入口和关闭自动校时的连接参数。现有 App 默认采集策略未切换到实验原型。

数据接收与磁盘写入通过有界队列隔离，队列超限与写入失败会使实验报错。原始音频按蓝牙连接与 AE22/AE23 来源分别保存；逐帧记录单调时间、序号、字节范围和控制事件。设备 8 位序号的重复/跳变仅作诊断，不擅自去重，也不把它当成全天全局时钟。

控制查询使用独立应答槽，采集期间另有消费者排空已记录的其他帧，避免状态通知长期积压。状态/时长查询前后核对文件身份；文件短暂未知时保留上一个已知身份。离线分析也会从快照重建文件变化，防止漏掉切段中间的短暂未知状态。

已通过 36 项原型自测与 7 项分析回归，覆盖：未知身份拒绝控制、不同文件不能判为恢复、计数不增长保持不确定、序号回绕/重复仍保留原始字节、队列与磁盘失败、残包不裁剪、真实 Opus 合成解码、到达空档不冒充静音，以及切段中间未知状态。合成测试不计为硬件通过。SwiftPM 全目标构建已通过；最终检查结果见本目录验证文件。

尚待验证：三小时实机边界结果、不同距离/多次恢复、掉电与系统重启、真正离线缺口修复、iOS 锁屏后台、低功耗模式语义、受控 VAD 与误漏检、未充电持续推流续航。当前这次长测处于充电状态，不用于证明电池续航。
