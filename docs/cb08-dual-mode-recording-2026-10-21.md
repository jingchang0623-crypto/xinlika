# 持续感知与主动重点记录：产品契约和 CB08 按键研究

> 产品定位：建设基于当前工程的开源心力球应用。三组观察、厂商前后台握手、保存回应变体和双向模式拨动已完成专用真机试次，结果按时间顺序记录于下文；早期段落中的“待验证”仅表示当时状态。当前进展另见 [原生 App 与本地服务原型](heartball-local-prototype-2026-10-21.md)。

日期：2026-10-21。按用户提供的两个核心场景，补充 Personal Agent 演进方案。资料研究与前三组观察阶段未发按键 ACK；后续已按授权实现并实测正常回应及明确标识的实验变体。没有修改固件、上传实验音频或删除卡上文件；单次协议握手不等同于 iOS 后台或长期可靠性验收。

## 两个同等重要的输入场景

| | 持续感知 | 主动重点记录 |
|---|---|---|
| 用户意图 | 在用户开启的持续记录时段内无感积累上下文 | 用户明确表示“这段值得保留”，按键开始、结束 |
| 边界 | 物理流连续接收，按语义形成事件，可跨分钟批次 | 有明确用户操作边界，独立逻辑记录，不混入整段日常摘要 |
| 处理节奏 | 分钟级封批、稳定事件、阶段汇总与选择性主动反馈 | 结束时尽快封好已收音频、优先处理，返回独立记录卡 |
| 输出 | 今日事件、人物/项目状态、未闭环事项和相关建议 | 原声与整理内容、灵感/决策/行动候选、关联项目 |
| 进入 Agent | 通过来源和归属判断后更新个人上下文 | 带明确“用户主动记录”意图；仍核对说话人、事实与承诺归属 |

两种场景共用证据、人物、项目和个人 Agent 状态。主动录音可以引用持续流中的范围，也可以对应独立设备文件；不能预先把产品上的“独立记录”等同于硬件一定新建一个文件。

主动录音无需先选择项目或设定目标，目标关联可以在结果中建议。低能量、短时长或低语音概率也不能直接作为删除明确主动片段的理由。用户主动记录视频/讲座时，可以作为参考素材整理，仍不将播放内容写成用户亲历；来源与录制意图分别保存。

“用户重视这段”“声音是谁说的”“识别是否正确”“是否允许执行行动”是不同属性。主动录了客户讲话，也不能把客户的承诺写成用户本人承诺。

## 厂商资料已明确的内容

在线复核声云仓库仍为固定提交 `f10cd9bf2a2341566d923818602ac93fb9246091`。iOS SDK 文档描述：连接 App 时，机身开始、保存、暂停、继续操作先以按键请求交给 App，再由 App 调用对应回应接口，设备才进入相应操作；文档另要求通知前后台状态。

SDK 上层 JSON 的 `cmd=8` 是按键事件类别，里面的 event 为 1/3/5/7。它不是可以直接照抄发送的 BLE TYPE/CMD。公开协议将机身事件放在 AE23，TYPE=3；SDK 暴露 `startBtnBackRecord`、`stopBtnBackRecord`、`pauseBtnBackRecord`、`continueBtnBackRecord`。

主要来源：[厂商 SDK 文档](https://github.com/SonicloudTech/sonicloud_opensdk/blob/f10cd9bf2a2341566d923818602ac93fb9246091/pnote-sdk-flutter-demo-main/iOS%20SDK开发文档(最新版本)-2026.04.23.md)、[PNode.h](https://github.com/SonicloudTech/sonicloud_opensdk/blob/f10cd9bf2a2341566d923818602ac93fb9246091/pnote-ios-sdk/PNode.h)。浏览器提取与哈希见 `research/cb08-dual-mode-2026-10-21/sources/index.json`。

补充对同一仓库 `libPNote.a` 的 arm64 静态检查：`DataEncapsulation` 中回应方法构造了以下候选 DATA。该证据来自 SDK，不是本台 CB08 的按键收发实测，未据此向设备发送。

| 请求类别 | 候选回应 DATA（不含帧头） | 证据范围 |
|---|---|---|
| 开始 | `03 02 01` | SDK `startBtnBackRecord` 构造 |
| 保存 | `03 04 01` | SDK `stopBtnBackRecord` 构造 |
| 暂停 | `03 06 01` | SDK `pauseBtnBackRecord` 构造 |
| 继续 | `03 08 01` | SDK `continueBtnBackRecord` 构造 |
| 前后台状态 | `00 12 state` | SDK `sendAppShowState:` 构造，固件行为未实测 |

此前 TYPE=3 App 发起 start/save 不生效，不能推出“物理按键回应也不生效”：App 主动控制与设备按键请求的回应是不同方向、不同命令。当前 App 控制用 TYPE=1，是真机已验证路径。

## 当前代码的具体缺口

1. `BLEClient` 尝试订阅 AE22 和 AE23，但连接就绪只以 AE22 为条件；AE23 订阅失败不能简单解释成硬件没有按键事件。
2. 现有代码有 TYPE=3 1/2、3/4 等常量，但没有找到专门处理机身请求并回复的业务路径。诊断日志和轮询状态不是按键状态机。
3. `expect()` 会消费不匹配的待收帧。机身事件不能长期依赖这个普通请求队列，需要独立事件分发，与状态查询、文件下载串行协调。
4. 正式客户端目前在 App 发起录音后断开连接，让设备独立录制；这条路径无法提供持续的按键事件连接和实时采集。
5. `ImportPolicy` 默认将小于 60 秒的新文件列入待确认。主动记一段十几秒灵感应按已确认意图和用户处理设置走优先路径，不能仅因短就被环境筛选规则挡住。历史未知来源文件仍保留原审核边界。
6. 卡上列表现有字段主要为文件名、大小和时长，没有在这些已核对接口中找到可靠的“主动重点/环境记录”标识。离线新增文件不能仅凭文件名或时长自动判断录制意图。

对应代码：`Sources/LuyinbiCore/BLEClient.swift`、`Sources/LuyinbiCore/RecordingControl.swift`、`iOS/AppModel.swift`、`iOS/ImportPolicy.swift`。

## 最大的硬件未知：两种场景能否同时存在

已有长测只验证了 TYPE=1 持续录制和一次蓝牙重连，没有按键人工操作标注，不能证明以下任何一种行为：

- 持续录音时按键是否能只标记一段重点，而保持底层录音不变。
- 是否会暂停/保存正在录的文件、切换到另一文件或等待 App 的回应。
- 再按一次是否有独立的“重点结束”事件，还是停止整个录音器。
- 与 App 断开时操作是否独立保存，重连能否恢复主动记录意图及边界。
- 长按/短按/双击、独立按键录音与 App 发起录音是否有不同语义。

目标实现分支如下，选哪个由真机证据决定：

| 实测能力 | 产品实现 |
|---|---|
| 能提供不破坏持续流的重点边界 | 在连续音频上建立 FocusRecord，引用起止位置和缺口，保持底层录音 |
| 按键确实改变录音状态或新建文件 | 把真实文件/流边界映射为重点记录，明确持续采集是否中断；恢复行为须符合用户设置并实测 |
| 无独立重点语义或离线没有可追溯标识 | 先用 App 明确的重点开始/结束入口，或区分互斥录制模式；硬件侧同步支持需厂商确认/固件能力，不能声称已实现 |

不能通过不回回应、随意回“成功”或偷偷重发 start 来冒充两种模式共存。尤其不能让用户按下停止后设备又在不明确的情况下续录。

## 数据与后端如何单独处理主动片段

新增 `FocusRecord`，最小字段建议为：

- 独立逻辑 ID、用户/设备/逻辑会话。
- 启动来源：机身按键、App 或来源未知；对应原始请求事件与确认状态。
- 主动开始/结束时间与精度；原始音频范围列表、关联卡上文件、哈希与缺口。
- 状态：请求中、记录中、结束待确认、可处理、结果就绪、不完整。
- 关联原声证据、转写版本、处理结果、项目和用户反馈。

用原始范围列表支持跨连接、跨物理文件的主动记录。不把按键通知到达时间当作经过校准的音频采样边界；需要与录音计数、样本位置和专用测试音核对。文件保存需等状态、完整目录及大小确认，不能只收到一个“保存”通知就导入尚未完成的文件。

主动结束可以促使手机封好当前短批次和尾段，优先进入处理队列，不要求等待下一次固定 60 秒计时，也不要求为了封批停掉硬件。若底层持续流已经有识别结果，优先复用；同一段音频同时属于环境事件和主动记录时，用原始位置关联同一次事件，防止生成两条相同承诺。

后台按意图选择整理方式：灵感保留原意并关联项目；对话呈现人物、关键判断和行动候选；明确备忘形成可纠正的条目。主动结束后提供独立卡片，再进入同一个 Personal Agent 的个人状态与跟进链路。用户主动记录只提高处理优先级，不自动提高 ASR 正确性或人物归属置信度。

App 分开表达三种状态：持续记录是否开启、重点记录是否进行中、设备当前是否真正在录。提供明确的全局暂停入口；重点结束与全局停止的含义需要让用户看懂，并与已验证硬件行为一致。

## 本轮已补的验证基础

实验模块增加 `DeviceButtonCandidate`，将入站 TYPE=3 的 1/3/5/7 标为按键请求候选。`CaptureJournal` 记录来源、时间、序号、候选类别和受限长度的控制载荷；不会自动 ACK、划定重点边界或宣称录音状态已改变。重复 8 位序号仍保留，不能把它当永久事件 ID 去重。

准备阶段原型自测由 58/58 扩至 60/60，通过候选过滤、重复序号保留及观察模式参数校验；采集分析测试 7/7、`cb08-probe` 构建通过。这些是模拟与构建结果，真机结果单独记录于本文末尾。

现有被动观察命令可为专用按键测试留证据，不启动、保存或自动回应设备：

```bash
.build/debug/cb08-probe capture --device UUID --observe-buttons --seconds 180 --output .build/新的按键证据目录
```

连接后厂商固件可能等待回应，所以这一观察步骤不是完整主动录音实现，也不能凭“按下去没录”断言按键坏了。ACK 实验仍须使用身份明确的专用测试，先验证实际请求和订阅状态；不在未知现有录音上盲目实验。

交互实验准备补充：`--observe-buttons` 现在允许设备空闲时持续等待人工按键，且要求 AE23 已成功订阅。新增通知订阅观察回调，将 AE22/AE23 的实际订阅状态及错误写入实验日志；不改变正式客户端的连接就绪条件，也没有启用按键自动响应。首次只读目录确认设备空闲、31 条已保存文件，探针随后退出并断开，等待用户执行第一组离线开始/结束。此时不能重新连接，以免污染“离线”条件。

## 下一轮真机矩阵与验收

| 专用测试条件 | 操作与需要的证据 |
|---|---|
| 未连接 App、设备空闲 | 人工按键开始/结束，随后读取完整目录；验证独立保存和文件边界，不猜测意图标识 |
| 已连接、设备空闲，先只观察 | 记录 AE23 订阅结果、实际按键请求、状态/文件名/计数；区分请求和已经执行的变化 |
| 专用文件的回应实验 | 仅对本次真实按键请求回应，核对状态与文件；不把回应发出当作操作成功 |
| 持续录音进行中 | 人工按键两次，查是否停流、保存、换文件或只发事件；保留音频、物理文件和时间映射，不自动重启 |
| 按键过程中断连、前后台或锁屏 | 记录请求/回应是否丢失、重复，离线是否保存、回连能否恢复意图与范围 |
| 5–20 秒短灵感及快速连续操作 | 不被环境短片筛选挡住；不丢字、不重复建立重点记录，结果与处理状态可见 |
| 下载同时按键 | 独立分发请求，协调传输和状态变化，不串文件、不让普通请求消费掉机身事件 |

最终需要能回答：按一次确实开始了哪段重点、按第二次确实结束在哪里、音频是否完整、底层持续记录发生了什么、App 是否生成且仅生成一条独立记录。之后再将该记录接入 Agent 的理解、主动反馈和纠正闭环。

## 第一组真机结果与第二组准备（2026-10-21）

用户确认已在探针断开后用机身键开始、结束并保存。前后完整目录从 31 条增至 32 条，唯一新增 `note20261021-094723.opus`，51,720 字节，设备目录时长 25 秒；原有条目未变化，下载前状态为 2（空闲）。完整下载大小一致且结束码为 0，按每包 40 字节/20ms 的固定解码方式得到 1,293 包、25.86 秒，严格解码成功。没有删除录音或上传音频。详见 `docs/validation/cb08-dual-mode-2026-10-21/offline-button-result.json`。

这证明本次离线按键操作后有独立保存且可解码的文件；离线期间没有按键事件连接，无法据此确认按下到采样的延迟、精确起止时刻或口述是否完整。文件名、时长本身也不提供可验证的主动意图标签。

第二组已建立仅观察连接，AE23 实际订阅成功，初始状态空闲，并进入 `waiting_for_manual_button`。不发开始/保存命令，不自动响应按键；等待用户只执行一次开始操作，再核对真实请求、录音状态和音频，以区分固件直接执行与等待 App 回应两种行为。原始证据保存在被忽略的 `.build/cb08-buttons-20261021/`。

## 第二组真机结果：连接空闲时的开始与保存

本次仅订阅/观察，不发送按键 ACK、App 前后台通知或开始命令。用户先后报告开始后显示录音、结束后显示停止保存。AE23 收到 TYPE=3/CMD=1 开始候选及 CMD=3 保存候选；开始候选约 1.987 秒后蓝牙断开，随后被动重连，查询到新文件正在录制并收到实时音频。断连原因尚未证实，不能把超时回退假说写成固件结论。

保存候选后仍有约 2.971 秒实时帧到达，首次空闲状态快照在候选后约 9.591 秒；这是帧到达和轮询观测时间，不是已校准的麦克风采样延迟。没有向设备发送保存命令，也没有自动重启。完整目录从 32 条增至 33 条，唯一新增 `note20261021-095150.opus`，150,760 字节，目录标记 75 秒，严格解码 75.38 秒，下载结束码为 0。原有文件未变化。

实时接收 883 帧、141,280 字节，落盘/索引核对无异常，严格解码成功。实时字节完整且唯一匹配卡上 `[9440,150720)` 范围，即卡上前 4.72 秒和末 0.02 秒未包含在这条实时流内（按 40 字节/20ms 基线换算）。因此按键通知时间不能直接当作完整主动记录的音频起止位置，当前可从卡上完整文件单独处理；不能宣称实时全段无损。未试听核对全文或调用 ASR。证据见 `docs/validation/cb08-dual-mode-2026-10-21/connected-idle-button-result.json`。

第三组已从新鲜空闲状态建立专用持续测试文件，确认 AE23 订阅和实时音频后才提示用户操作；不会收到停止请求后自动续录。该组仍为无按键 ACK 条件，不能代替厂商完整握手路径的结论。

## 第三组真机结果：持续录音中执行保存手势

设备新鲜空闲、完整目录 33 条后，由探针发送一次 TYPE=1 开始命令，新建并确认专用文件 `note20261021-095427.opus`，持续接收实时音频。用户执行与第二组结束时相同的机身操作，报告停止保存；AE23 收到 TYPE=3/CMD=3 保存候选。其后最后音频帧到达间隔约 2.969 秒，首次空闲快照约 6.977 秒。最终确认设备状态 2，没有新流或替代文件；观察结束的可选保存逻辑因设备已空闲而跳过，未发送保存/重启或按键回应命令。

完整目录增至 34 条，只新增本次专用文件，原有条目均未变化。下载完整 412,240 字节、结束码 0，严格解码 206.12 秒。实时音频共 2,576 帧、412,160 字节，严格解码成功；完整且唯一匹配卡上 `[0,412160)`，仅卡上末 80 字节（40ms 基线）未在实时流中收到，没有内部字节缺口或落盘丢弃。这个范围结论不等同于麦克风声学全程无损，也没有核对用户口述的前后标记是否全部入音。

**本次手势确实结束了整个物理录音，没有观测到保持持续流的重点标记，也没有独立的重点开始/结束配对。** 仅一个观察模式试次，不能扩展为所有手势、所有固件或完整厂商握手都无法提供其他行为。详细证据：`docs/validation/cb08-dual-mode-2026-10-21/continuous-button-result.json`。

## 三组结论与开源心力球应用的实现约束

| 条件（各一次） | 已实测 | 仍未验证 |
|---|---|---|
| 离线主动开始/结束 | 新建独立文件，完整保存并解码 25.86 秒 | 离线逐次按键事件、精确声学边界、自动意图恢复 |
| 已连接空闲，主动开始/结束 | 可观察开始/保存候选；新建文件并完整保存 75.38 秒；开始后有一次断连 | 完整 ACK/前后台握手下是否仍断连；不漏起音的实时交付 |

已增加独立原生 `HeartballLab` 与本地持久服务。一次 211.06 秒完整卡上录音中，实时接收 210.96 秒，创建 26.08、3.12、77.52 秒三个重点；最长一段跨三个批次。重点操作没有向硬件发命令，结束重点后仍采集同一文件；全局结束才保存，完整卡上参考保留了实时末尾未收到的 0.10 秒。六个批次、三条重点及对应任务在完成态服务重启后保持一致，重复结束没有产生第二条重点任务。

这已经验证 App 上的非破坏重点范围与独立任务，不代表机身键标记、精确声学边界、转写整理或 Agent 反馈通过。全部音频仍在本机，ASR 调用、外部上传、个人记忆写入和卡上删除均为 0。设备恢复普通档，测试已结束；目前只保留空闲的 App 和本机服务。使用方式、证据与限制见 [原生原型说明](heartball-local-prototype-2026-10-21.md)。
