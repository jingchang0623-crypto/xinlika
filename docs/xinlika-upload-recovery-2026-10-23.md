# iPhone 上传积压与状态误报修复

2026-10-23。用户截图显示持续录音已接收 35,901 秒、待传 160 项，下方仍显示“录音已上传，自动整理中”。用户补充：后来反复点击的是总入口“重试连接和待传录音”，而非逐条处理任务的重试。

## 证据与边界

只读检查实体 iPhone，安装版本为 0.3.7（25）。本轮未重启 App、停止录音或改动已上传原声。读取时这轮会话仍为 recording，手机保留原始接收流及缺口记录；截图后的手工操作已使当前会话绝大多数消息进入 accepted，剩余一项正常待传。另有历史服务的隔离证据，不能将其计为当前云端待传。

今日传输回执的修改时间出现多处长空档，包括约 27、48、90、84、57 分钟。抽查这些空档前后的 12 份回执均为 HTTP 200，没有错误码；绝大多数消息最终只执行了一次成功确认。这与“录音一直积累、上传一段时间没有推进、之后成批传完”的表现一致。回执时间不能证明请求何时开始、App 何时被挂起或网络当时是否可用，因此不能据此唯一确定系统层根因。

代码中已确认的风险是：所有手机小批次均串行等待系统后台 URLSession；该 session 同时服务旧文件传输，资源超时达 24 小时，另有最长 900 秒的系统延迟。一个迟迟不结束的请求会占住整个上传工作器；再次点击总重试也不能越过仍被占用的工作器。此外，任意一项成功即写入全局“已上传”文字，读取整理结果又覆盖成“已同步”，没有以剩余待传数量约束状态。

本机最初云端 HTTP/SSH 只读核查未连通。后续一次直接 HTTP 查询成功，确认本轮已保存、等待卡上原声核对，返回的 760 项处理任务均为 completed；最终核对状态查询又遇到 TLS 握手超时，系统 HTTP／SOCKS 代理路径也未成功。未因此认定云端宕机，也未排除服务端另有延迟。没有修改或重启云端服务。

## 改动

- 小批次先通过普通 URLSession 即时发送：请求等待 20 秒、资源上限 45 秒，显式允许蜂窝、昂贵与低数据网络。每次短传输持有系统后台执行额度，锁屏本身不取消请求。
- OS 执行额度耗尽时交给现有系统后台文件上传；应用获得执行时间后，90 秒看门狗可取消不返回的 POST 并交回重试队列。没有修改旧 PUT 的长文件恢复协议。系统挂起时计时器仍受 OS 限制，不能宣称有严格的后台墙钟时限。
- 系统后台任务的恢复检查异步进行，避免后台 daemon 的任务枚举占住即时上传入口。重放沿用原消息 ID、正文、音频哈希、服务归属与原有服务端幂等回执；极端恢复竞态可能重复发送同一请求，不会创建另一份音频身份。
- 独立、可测试的串行上传协调器连续排空队列；网络错误、HTTP 0、408、429 和 5xx 自动以 2/4/8/16/30 秒退避，最大 30 秒。文件变化通知只启动停止的工作器，不打断退避；网络恢复、进入前台及手工重试可唤醒等待。
- 401/403 停止自动推进，等待凭据修复／明确重试；其他永久拒绝保留证据，隔离该会话，不让同会话后续消息越过拒绝点。不会为消除“待传”数字而删除数据或跳过音频范围。
- 状态根据当前待传、隔离、请求阶段、服务可读性与处理任务共同计算。待传 160 项时必定显示数量及上传／等待恢复状态，不能再显示全部录音已上传；转写／整理失败也不会被显示成处理完成。
- 诊断状态增加上传阶段、最近 HTTP 状态、最近确认时间及隔离数量，不保存密钥或转写正文。
