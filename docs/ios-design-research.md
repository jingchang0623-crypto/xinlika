# 深脑 iPhone：Apple 设计研究与改版建议

日期：2026-09-05。范围：现有 0.1.2 全 App 信息架构与分析阅读体验；本轮是研究与方案，没有修改 App 代码、安装包或用户数据。

## 结论

建议采用「内容列表 + 简报卡片 + 长文阅读器」。卡片适合摘要和相对独立的判断，不适合把两万字分析逐段装进相同容器。
参考 Apple 健康的概览到详情、备忘录的章节组织、Safari 阅读器的去干扰阅读。借鉴各自解决问题的方式，不把几个 App 的装饰拼贴在一起。

这是针对深脑的设计判断，不是 Apple 官方提供的“AI 分析卡片模板”。

## 当前界面的具体问题

依据：RootView.swift、MeetingView.swift、上一轮模拟器结果页截图，以及真实缓存正文的结构统计。截图是标记过的测试样例；真实正文仅在本地统计结构，没有发到搜索服务。

1. **产品主次倒置。** 默认入口是设备连接。记录列表先显示处理状态、文件体积、手机留档，再进入内容；日常回来阅读时，需要越过采集工具的语言。
2. **报告采用设置表单的视觉语法。** MeetingView 的标题、完成状态、更新时间分别成为列表行；摘要、分析、判断都是相近的白色圆角分组，内容权重不清晰。现在不是没有卡片，而是卡片边界没有表达重要性。
3. **Markdown 结构没有正确表达。** MarkdownBody 按空行切段，所有以 # 开头的段落统一为 headline，其余只有行内格式。没有真正的分级标题、块级列表或表格渲染。
4. **数据长度已超过当前排版能力。** 两份分析约 8,500 和 21,400 字符；长的一份含 49 个标题、37 行列表语法、141 行表格语法。141 是表格语法行数，包含分隔行，不是 141 张表。
5. **阅读操作离内容太远。** 行动项在完整长文之后，回听入口又在所有内容底部；没有章节目录或阅读位置恢复。用户不得不长距离滚动。
6. **视觉语言还没有形成系统。** 设备页是宣传语和状态卡；记录页是技术台账；结果页是长表单；账号页包含 Ogg、处理台账等实现术语。三种任务需要不同布局，但应共享字体、颜色、边距、控件和语气。

上一轮 UI 测试只验证结果能打开和样例文本可见，不能代表长报告的视觉质量已经验收。

## Apple 规范真正支持什么

### 内容优先，按重要性组织

Apple 要求关键内容获得足够空间，不要被次要信息挤压；可以通过留白、背景和分隔形成分组，并逐步展示复杂内容。对深脑的推导是：首屏应呈现会议主题和实质摘要，把文件大小、刷新时间、分析方法等降到次级位置。[HIG：Layout](https://developer.apple.com/design/human-interface-guidelines/layout)

当前 Design principles 页面于 2026-06-08 更新，强调用途、用户自主性、责任、熟悉感、适应性、简明、细节品质与愉悦。这里最重要的是让用户直接到达内容，同时保留恢复错误和控制数据的能力；不能为了简洁隐藏失败状态。[HIG：Design principles](https://developer.apple.com/design/human-interface-guidelines/design-principles)

### 文字不是图片网格

Apple 的 Collections 指南认为集合布局通常适合图像内容，文字往往更适合可滚动的列表。这里的 table 是列表式 table view，不是在建议把文章做成电子表格。深脑记录首页应优先纵向、整行可点击的内容列表，不做双列文字卡片瀑布流。[HIG：Collections](https://developer.apple.com/design/human-interface-guidelines/collections)

### 层次主要靠排版，不靠大量容器

iOS 建议默认文字尺寸为 17 pt；系统文字样式提供层次和 Dynamic Type 支持。长段落可增加行距，三行以上内容应避免紧凑行距。深脑应采用系统字体、明确的标题级别和舒适的中文段落节奏，而不是将小号灰字当作精致。[HIG：Typography](https://developer.apple.com/design/human-interface-guidelines/typography)

### Liquid Glass 属于操作层

Apple 明确区分内容层与导航/控件层，要求不要把 Liquid Glass 放进内容层。深脑可以让系统导航栏、标签栏采用系统外观，分析正文与摘要卡使用稳定、易读的背景；不叠加透明玻璃卡或发光渐变。[HIG：Materials](https://developer.apple.com/design/human-interface-guidelines/materials)

### 可访问性决定设计是否完整

支持大字、明暗外观、足够对比度、VoiceOver，状态不能只靠颜色。Apple 当前表格将 iOS 默认控件尺寸列为 44×44 pt；本方案把不小于这个点击区域作为项目验收目标，不把它误称为文档唯一的绝对最小值。[HIG：Accessibility](https://developer.apple.com/design/human-interface-guidelines/accessibility)

## 可以借鉴的 Apple 样式

| 参考 | 借鉴什么 | 不照搬什么 |
| --- | --- | --- |
| Apple 健康 | 概览先给重要信息，再点开详情；不同主题可独立浏览 | 不造与录音无关的大数字、趋势图和仪表盘 |
| Apple 备忘录 | 连续文档、标题和副标题、可收起的章节、表格 | 不把阅读页变成复杂编辑器，不默认折叠全部正文 |
| Safari 阅读器 | 减少干扰、保留正文，长页面用目录辅助定位 | 不把每份报告强制打开成外部网页 |

官方实例：[健康的摘要与提要](https://support.apple.com/zh-cn/guide/iphone/iphe3d379c32/ios)、[备忘录的格式与可折叠章节](https://support.apple.com/zh-cn/guide/iphone/iph1ac0b3a2/ios)、[Safari 阅读器](https://support.apple.com/zh-cn/guide/iphone/iphdc30e3b86/ios)。

### 三种可选方向

| 方向 | 优点 | 代价 | 判断 |
| --- | --- | --- | --- |
| 纯阅读器 | 连贯、干净，适合深入阅读 | 第一眼仍难抓重点 | 适合完整分析，不足以承担整个 App |
| 全卡片 | 独立内容容易扫读 | 长文割裂，重复留白，滚动变长 | 仅用于概览，不作为全文默认样式 |
| 简报卡片 + 阅读器 | 同时服务快速回顾和深入理解 | 需要一个清楚的概览/全文切换 | 推荐 |

## 推荐的全 App 结构

底部保留三个稳定入口：**记录 / 设备 / 设置**。默认进入记录，设备是同步录音的工具，设置承载账号和帮助。不要把“同步”这种动作做成 Tab。依据是 Apple 的顶级导航规范；具体名称和排序是本项目提案。[HIG：Tab bars](https://developer.apple.com/design/human-interface-guidelines/tab-bars)

### 记录首页：内容索引

- 每条显示最多两行标题、录音日期与时长、一到两行摘要预览；整行点击打开结果。
- 一个清楚的状态说明即可。进行中/失败时突出必要动作，正常完成后不叠加多个绿色成功标签。
- 录音日期使用可靠的录音时间，不把缓存更新时间当成会议日期。
- 技术信息和完整同步过程放到详情。搜索首先限定为“本机已有记录”，云端历史未接入前不暗示已经覆盖全部内容。

### 结果概览：少量有意义的卡片

以下是信息结构示意，不是最终视觉稿：

```text
会议主题                       更多
录音日期 · 时长 · 参与者

概览  |  完整分析             转写与回听

[ 本次摘要 ]
现有摘要的清晰预览，必要时展开全文

关键判断
[ 判断正文                  查看原话 ]
[ 判断正文                  查看原话 ]

行动项
事项 / 负责人 / 时间
事项 / 负责人 / 时间
```

- 卡片边界对应一个独立摘要或判断，不对应每一个自然段。正文不再套一层同样的卡片。
- 概览只使用现有 summary、judgments、commitments，不为了排版额外触发 AI 分析，不伪造“一句话结论”。
- 原话默认收起，点击在上下文中展开。没有可靠音频时间戳时，不伪装成可跳转的原声定位。
- 行动项首版可阅读和复制。跨端完成状态尚无实现时，不放看似能同步的完成复选框。

### 完整分析：可持续阅读的文档

- 大标题和精简元数据之后进入连续正文，明确区分章标题、节标题、正文、引用、列表和表格。
- 目录按真实标题级别组织，先显示一级/二级，避免把 49 个标题平铺成菜单。
- 保留并恢复阅读位置；刷新不能将用户突然带回顶部。
- 表格单独处理：键值型适合纵向标签和值；需要横向比较的矩阵保留行列关系，局部横向滚动或点开查看，不让整个页面横向溢出。
- 不删减或改写原文以求“好看”；对长内容做导航和展开，而不是静默截断。
- 返回、目录、转写/回听和更多操作放在可到达的控件区，不藏在两万字之后。优先系统导航；专注阅读模式若需要全屏，作为明确的独立模式提供。

### 设备页：状态清楚，操作直接

设备身份、是否可用、电量、最近同步时间在一处；活动任务显示阶段和真实进度，提供暂停/恢复。固件版本、RSSI、字节和诊断放入设备详情。保留有意义的错误解释，不用宣传语替代当前状态。

### 设置与登录：系统熟悉感

保留原生分组表单，统一文字风格。账号、支持与版本信息清楚分组；开发连接参数继续只出现在开发环境。将 Ogg、处理台账等术语替换为录音、同步、分析等用户语言。

## 视觉规范起点

以下数值是待真机验证的项目提案，不是 Apple 强制的圆角/边距标准。

| 元素 | 起点 |
| --- | --- |
| 字体 | 系统字体与语义文字样式，不嵌入字体包；中文交给系统字体回退 |
| 正文 | 默认 17 pt，长文可以测试 18 pt；随 Dynamic Type 缩放 |
| 报告标题 / 章节 | 标题约 28 pt；主要章节约 20–22 pt，次级标题以字重和间距区分 |
| 辅助信息 | 13–15 pt，仅承载日期、来源等次要信息；重要解释不缩成浅灰小字 |
| 页面边距 | 约 20 pt；优先尊重系统安全区和尺寸变化 |
| 卡片 | 约 16 pt 内边距、16 pt 圆角；轻背景区分，避免同时叠边框和重阴影 |
| 阅读节奏 | 段间约 12–16 pt，章节间约 24–32 pt；行距随字体放大，不固定高度裁字 |
| 颜色 | 系统内容背景与分组背景，主要文字用语义前景色；保留深脑蓝用于操作和选中状态 |
| 状态色 | 成功/警告/失败按语义使用，配文字或符号，不给每张内容卡随机分配颜色 |
| 深色模式 | 跟随系统，验证实际对比度；不把明亮配色机械反转 |

品牌识别来自少量稳定的蓝色强调、统一图标和排版节奏；不是大面积渐变、装饰波形或所有模块都带图标。

## 实施顺序与出口标准

1. **先确认三张实尺寸设计稿**：记录首页、结果概览、完整分析；用匿名化的长报告结构，不仅用两段短样例。设计稿明确哪些数据是示例。
2. **建立共享视觉组件**：字体/颜色/间距、记录行、摘要卡、状态提示、分析文档块。保留 SwiftUI 原生导航和表单。
3. **修正 Markdown 渲染，再做长文导航**：按文档语法结构渲染，不再靠空行与 # 前缀猜测。未知块保留可读回退，避免文本丢失。
4. **统一设备与设置页**：不改蓝牙、后台上传、账号隔离和幂等逻辑；视觉改动与可靠性改动分别回归。

设计验收目标：

- 普通记录第一眼能识别主题；打开后不用穿过多行技术状态就能看到摘要。
- 完整长报告没有原始表格管道符泄漏、层级丢失、内容截断或全页横向溢出。
- 小屏、大字、深色模式和 VoiceOver 可用；点击区域、对比度和底部安全区经过检查。
- 2 万字内容滚动顺畅，切换概览/全文和前后台不丢阅读位置。
- 上传中、分析中、未自动分析、失败、离线缓存都有完整样式与可靠操作，不只做成功截图。
- 原有 34 项 iOS 测试继续通过，并添加长文/表格/大字 UI 场景；不以测试数量代替视觉验收。

研究边界：本轮阅读 Apple 官方现行指南和三个官方应用使用实例；代码覆盖当前三个顶级页面，视觉依据包含上一轮结果页截图。没有宣称已经对全部真机页面做新版视觉验证，也没有执行完整 Impeccable 网页检测或品牌建档。采用其信息层级、减轻认知负担和排版检查作为辅助。
