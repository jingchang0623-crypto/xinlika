# 心力卡 iPhone 0.3.0：手机拥有采集与上传

2026-10-21。就地复用 `codex/iphone-testflight-mvp` 的现有 iOS 工程和未提交实现；bundle 仍为 `com.zaowuyun.shennao`，0.3.0 (12) 覆盖安装到已连接 iPhone 16 Pro，未卸载或清除旧容器，未提交、推送或发布。

## 手机侧

- 新主入口为今天、主题、记忆和聊天、录音卡。今天直接使用服务的完整当天投影，会议/对话可折叠展开；普通事项不增加逐条确认。原文、原声、内容及来源纠正接现有处理协议。
- 独立 `XinlikaModel` 持有采集生命周期，场景转后台不再断开或取消实时接收；旧深脑登录、同步与 Mac capture API 不参与手机开始录音。原旧路由与测试入口保留在显式 legacy/fixture 路径。
- 复用 BLEClient、FrameParser、RecordingControl、RecorderButtonHandshake、Ogg 和现有 DownloadCheckpoint。实时 AE22 音频由同步串行磁盘入口接纳，不建立无限内存队列；原声 fsync 后才写接收日志。数据保护允许首次解锁后锁屏访问。
- 逻辑会话、物理卡文件、连接流、完整包边界、接收时间、序号、哈希、重点和缺口持久化。默认 60 秒，允许最大 300 秒封批，保存时封尾；重点只封软件批次，不发送硬件停止命令。
- 进程中断恢复日志已提交的原声并登记缺口；断连后重新发现特征与订阅，只在原文件及录音状态核对后接纳声音，不自动 start/resume。超过 2 秒到达间隔保守登记待核对缺口；没有把它直接判为确实丢样。
- 上传是不可变 JSON 文件消息，复用系统后台 URLSession、完成回执和重新附着。网络重传保持消息身份与音频哈希；服务拒绝后显示阻塞，瞬态错误按退避等待。普通网络补传不会消除蓝牙漏采提示。
- 保存后可明确点击“核对卡上原声”，仅设备空闲且文件身份/大小稳定时断点下载。完整大小、结束码、哈希、唯一字节对齐通过后保留参考及漏采范围；小尾段/语义补齐仍进入审核任务，不伪造词级拼接。

## 独立服务

`scripts/heartball-mobile-service.py` 不实例化 Mac Engine，不调用蓝牙或采集子进程；直接拒绝 capture/focus 硬件控制路由，并拒绝使用活跃 `.build/heartball-lab` 数据目录。

- `/v1/mobile/capabilities` 核对手机协议；`/v1/mobile/ingest` 接收批次、缺口、重点、结束和分块卡参考。认证、包长、顺序、身份及哈希校验先于接纳；重复同消息回执幂等，改写同身份返回冲突。
- 复用现有 Store、AgentStore、voxgate、LangGraph/SQLite、事件归并、记忆问答和反馈；不另建第二套记忆框架。录制时间按每个连接流的手机接收锚点及字节偏移估算，不使用上传/处理时刻，也不声称 ADC 或词级精确。
- 修复 voxgate 明确 `concurrency_exceeded` 时误报鉴权/额度的问题：按忙碌等待，保留已完成转写，等待不消耗抽取重试。其他鉴权/额度错误仍阻塞。未修改或重启已有 ASR。
- 默认 loopback；局域网需显式指定私有接口，拒绝通配公网绑定。手机允许 HTTPS 或私有 HTTP 地址。没有将原 Mac loopback 服务代理/公开到局域网。

当前正常手机服务运行于 `.build/xinlika-mobile`，新端口 18777；连接文件只在私有 runtime 与手机容器。它是独立账本，**没有迁移或公开 Mac 已有历史**，手机今天仅展示该服务已有事项。测试服务 `.build/xinlika-mobile-dev` (18776) 已结束监听，证据保留。

复现独立处理服务（替换私有地址与配置路径）：

```sh
.build/heartball-agent-env/bin/python scripts/heartball-mobile-service.py \
  --root .build/xinlika-mobile --host YOUR_PRIVATE_LAN_IP --port 18777 \
  --processing-config /absolute/private/processing.json
```

## 真实采集证据与验收边界

用户确认锁屏并保持后台后，独立手机服务中断 74.6 秒，手机原声从 439,520 增至 591,040 字节，仍为同一连接流、缺口 0，待传数量增加；恢复服务后六个批次已到达。锁屏期间服务端完成 30 字及 29 字非空转写与普通整理。这是本次有限时长锁屏/后台与服务不可达补传的实测，尚不等于系统强制终止后的自动后台重启或全天续航通过。

首次故障样本完整卡上原声 642,960 字节；两段实时原声全量唯一匹配范围 [0,286400) 与 [290880,642880)，中间 4,480 字节（2.24 秒）及末尾 80 字节（40ms）由完整卡上参考保留。它保留作恢复故障样本，不计持续性通过。


正常主测试 session `e8148224-e66b-4058-97e5-20953be1922b` 的完整卡文件为 1,926,720 字节（963.36 秒），身份、大小、结束码、SHA-256、实时流全量唯一字节对齐和严格解码通过。实际实时覆盖为 [0,1129440)、[1136480,1190240)、[1190880,1487040)，缺失实时范围分别 3.52 秒、0.32 秒、219.84 秒；最后一段对应蓝牙关闭后没有恢复推流，**不是零丢样或蓝牙恢复通过**。

服务将 219.84 秒的未覆盖原声拆成四个互不重叠的稳定修复批次（60/60/60/39.84 秒），复用已有 ASR/整理流程；四批均完成，返回文本长度为 0/0/0/1。这证明缺失原声的处理链路，不证明其中有有效语音或语义质量通过。两个短缺口共 3.84 秒保留完整参考及上下文核对任务，没有单独向 ASR 发送亚秒尾音或伪造词级拼接。四个重点边界产生的小批次仍有 ASR InternalServerError，原声保留、任务未标成功；另一个正常重点已得到 15 字非空整理。总共三个重点范围均保存，重点未发送硬件启停命令。

一次显式 App 更新/重启后，原文件恢复接收，保留为不同连接流及待核对缺口；没有因此宣称系统杀进程后的自动唤醒通过。主测试最终有三个实时流。机身蓝牙超范围往返并未实际测试；关闭/开启蓝牙是不同条件，不能代替。

## 蓝牙关闭/开启的已知阻塞

专用短测试 `ea2ed088-7bce-4fd2-8952-b5bf96f54d8b` 中，用户再次关闭蓝牙约十秒并开启。修复了 poweredOff 后缓存连接误报及恢复过早标为 live 的问题，但重连后仍停在 121,280 字节（60.64 秒）：只能读回原文件和录音状态，未恢复音频。

在明确隔离的测试中，一次继续命令 `1-3-0` 及强制重建 GATT 通知都没有恢复声音；一次 `1-0` 切换到了新的卡文件 `note20261021-174542.opus`，没有接续原文件。应用发现身份变化后停止接纳，没有拼到原会话。用户随后明确回复“已保存实验录音”，正常保存新文件。原测试文件 `note20261021-173757.opus` 已由手机完整下载、上传并唯一字节对齐：929,680 字节（464.84 秒），严格解码退出码 0；实时覆盖 [0,121280)，其余 [121280,929680) 保留并排入七个独立修复批次，七批 ASR 与普通整理已完成。新实验文件保存在卡上，没有删除。所有实验性重发/重订阅入口随后从代码移除，正常重连仍不自动 start/resume。

这轮只能验收锁屏后台采集、有限时长服务不可达后补传、正常重点及完整卡参考核对；**蓝牙关闭后同文件实时推流恢复仍未通过**。当前安全使用路径是结束并保存，再核对卡上原声，明确开始下一段；不承诺断连期间手机实时内容已恢复。完整原声已保存并不等于所有短尾语义已处理。

界面区分“待传”与“校验冲突保留”：初轮故障的 11 项仍原样保留并隔离，不阻塞新会话，也不再伪装为网络补传。未收到音频时显示恢复/等待状态；参考完成后显示完整卡文件保留，不再重复提示字节核对尚未完成。
