# 心力卡事件边界、跨对话关联与证据成本修复

本轮沿用冻结转写，没有调用 ASR、操作录音卡、写生产库或重启现有服务。上轮 10 月 22 日的两个留出录制组不再送模型调优；本轮另建独立参照，开发通过后才执行一次对照。

## 修复的位置

先前误归并并非初次提炼造成：增量步骤正确区分了内容风格问题与 iPad 引用问题，滚动步骤随后将它们概括成一个更宽的“约束问题”。新版 Skill 增加“是否能分别解决、分别验收”的边界检查，禁止用更宽标题掩盖独立问题。把旧的真实错误归并原样交给新复核器，得到拒绝结果；该项是开发回归，不是新盲测。

跨对话漏关联时，相关原文已经召回。问题包括事件与主题的层级混淆，以及把原始会议 ID 丢给模型后，模型未正确使用共同上下文。

- 事件仍按具体问题保持独立；主题可表示有明确范围的持续活动，允许每轮讨论不同子问题。
- 新增可选 `CrossConversationReview`：在增量和滚动整理之后，对有界候选补一次主题关系复核，复用 `AgentDomain.task/commit`，不新建另一套图或记忆库。
- 宿主把用户曾提供的相同会话 `group_id` 规范成共享上下文及其成员列表；明确注明它不是“同一事项”的答案。语义关系仍需两端原句支持。
- 每条边必须包含两端事件各自的逐字引用，绑定版本、权限和原文签名。只允许写主题，不改事件身份、录制时间、原文或个人事实。
- 同一来源水位的空关系也是终态，不能轮询模型直到出现关系；每次最多两次调用，第二次仅修结构与引用错误。

复核入口复用版本化 review Skill，通过 `operation=cross_conversation_links` 与滚动归并复核区分。没有另写通用 Agent 循环。`NativeProcessor` 已有显式开关 `cross_conversation_review`；默认关闭，旧处理路径保持兼容。

## 开发与独立材料

开发使用三段完整的已捕获会议录制，共 9 份原文、57 个片段。它们属于已使用的开发日，不声称是独立数据或覆盖了整场两小时会议。检查同一画面评审的跨对话关联、模型选择不误关联，以及风格问题和 iPad 引用问题分开。

v3 仅改边界与主题层级，开发 2/3；v4 增加整理后复核，仍 2/3；v5进一步明确活动层级，仍 2/3。错误与成本均保留。v6 保持 v5 的 Skill 内容，新增宿主共享上下文表达后，开发达到 3/3，57/57 片段分配核对通过。v6 不再重复购买已测开发基线；这不是宣称代码改动的因果收益。

新的独立材料有 13 份原文，来自 22 日上午完整的两条产品反馈，以及 23 日晚已捕获的播放／产品展示上下文。只选择这些完整语义片段，不声称是两份数小时录音的全量覆盖。与旧留出组和开发原文的文档 ID 重叠均为零。

用户在候选独立验收前确认：22 日“过滤路上节目、旁人电话”与 23 日“展示电视剧情被全天记录”的两段，是同一事项的延续。该确认作为评分标签放在输入之外，没有交给执行模型，也没有手工建立待验收主题关系。

独立五项检查：跨对话正向关联；跨录制两次事件保持身份；过滤与重点按键问题分开；明确的按键短反馈可见；播放剧情与产品展示分开。标签与评分函数先冻结。候选和代码冻结后再跑独立对照，结果不再用于修改提示词。

这些参照核对事项身份和既有 ASR 引用，不代表逐字听音真值、声纹准确率或全天关联召回率。

## 证据成本

Harness² 的编辑器通道已改为内容寻址：文件路径指向 SHA-256，完整文本按哈希保存一次。所有路径与原文可逐字还原；不裁剪、重写或语义摘要。文件路径仍保留原有证据角色，防止去重丢掉基线／候选对应关系。

对上轮同一份开发反思请求做真实兼容验证：

| 指标 | 原通道 | 内容寻址通道 |
|---|---:|---:|
| 文件路径 | 75 | 75 |
| 唯一文本 | 重复发送 | 24 份 |
| 输入 tokens | 353,455 | 132,910 |
| 总 tokens | 354,278 | 133,464 |

输入 tokens 实测减少 **62.40%**，证据完整还原校验通过，模型返回可用 XML 反思。该请求只用旧开发证据，不含任何新旧留出内容，没有修改候选 Skill。这是相同证据传递的成本对比，不将不同大小数据集的总调用数冒充优化收益；金额未核实。

最终开发候选通过 3/3；独立对照已完成，结果如下：

| 新注册的独立检查 | 基线 | v6 候选 |
|---|---|---|
| 用户确认的播放内容处理跨对话延续 | 通过 | 通过 |
| 两次录制的事件保留各自身份 | 通过 | 通过 |
| 过滤问题与物理重点按键问题分开 | 通过 | 通过 |
| 明确按键短反馈保留 | 通过 | 通过 |
| 播放剧情与产品演示分开 | 通过 | 通过 |

基线和候选都是 **5/5**，不能据此宣称新材料上总体准确率提升。候选修复的是开发集中已知漏关联，并在新增独立材料上没有出现这五项回归。人工检查最终关系：开发集连接同一创作成果评审中的风格、动作、构图反馈；独立集连接过滤无关内容与随后展示记录摘要，没有手工写入待测试边。

开发候选 57/57 片段、独立候选 83/83 片段的最终分配均通过：原文未变、没有丢失、重复或过期范围；个人事实写入数为零。候选分别显示 9、10 件事件，数量本身不作为质量分数。

同一独立材料上，基线 7 次调用／36,841 tokens，候选 9 次／51,172 tokens，增加 **38.90%**。额外关联复核提高了处理开销；不能把编辑器节省与在线整理成本混为一谈。

本任务全部实际消耗 **66 次调用、393,212 tokens**：输入 367,884、输出 25,328，包含 v3/v4/v5 开发失败、v6 开发、一次独立对照、去重兼容验证和真实误归并复核。所有调用有 provider usage，金额未知。既有上轮实验消耗未重复加入本轮。

结果：[完整脱敏回执](validation/xinlika-event-links-2026-10-24/result.json)。

### 已接入的运行方式

后续实际部署：2026-10-24 已按用户指令启用到云端新增来源链路，并完成双端真实纠正验证；现场发现的宿主纠正血缘修复注册为 profile revision 2，Skill 内容不变。部署、实测范围及尚未通过的最终投影审计见 [云端启用结果](xinlika-v6-cloud-2026-10-24.md)。以下保留本轮原始实验与注册时点说明，不把后续启用混写成原盲测结果。

通过本轮小样本门槛的配置注册为 `xinlika-events-v6`。在现有 `agent_runtime` 配置对象中显式增加以下字段即可选用，原模型接口与凭据配置继续保留：

```json
{"processing_profile":"xinlika-events-v6"}
```

配置加载器校验验收证据、Skill 内容哈希及执行源码哈希，合并增量、滚动、跨对话复核开关及显式片段编号协议，保留原端点、凭据和其他配置。不加载未验收版本，也不改变无 profile 的默认行为。资源随源码包完整导出，可在后续安全启动／部署时启用；本轮没有热切换或重启正在工作的服务，默认 v1 未改变。

验证完成后补充的是启用与缓存保护：代码／模型／Skill 版本定义复核 epoch；每个新 epoch 初始化时仅登记已有历史基线，后续新增来源才触发处理，避免升级时重扫整档。不同 worker 的初始化在一个事务内完成。空关系不会永远跨版本复用，也不会被同版本反复付费重试。这些保护不更改复核模型输入；技术测试验证 epoch 变化时输入保持一致，本轮没有再调用模型或重复独立测试。

本轮只验证少量已捕获场景和一个新增跨对话正例，不代表全天召回、声音来源分类或进程崩溃后的关联任务恢复已经完成长测。关联候选有数量、上下文长度和权限边界，用户记录、问答与记忆仍由原有权威账本管理。

新入口 `scripts/validate-xinlika-skills.py` 运行指定 Skill 的匹配对照，不冒充新一轮 Harness² 自动提议。每轮账本不可覆盖；独立集只允许一次完整评估，其后禁止换候选反复测试。原文、模型输出、标签与密钥仅留 `.build`。

验收之后没有继续改语义提示词或模型参数。231 项相关测试通过，干净源码导出包可完整校验并加载 v6 profile；已有实验重试返回原结果，新增模型调用为零。开发与独立对照使用同一冻结执行源码，候选内容未变，注册标签未变。详见 [工程核对](validation/xinlika-event-links-2026-10-24/verification.json)。
