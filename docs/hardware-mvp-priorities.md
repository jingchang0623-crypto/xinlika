# 硬件与 App 优化：第一性原理与 MVP 决策

日期：2026-09-06。状态：0.1.4 已完成开发、83 项自动化测试和模拟器启动验收，最新落地记录见 [0.1.4 实施与验证](ios-0.1.4.md)。下方代码现状为决策时基线，真实硬件与行为验证仍需单独完成。

本轮用户补充了最关键的实际反馈：**“硬件和 APP 互动太麻烦了，每次都要操作和等待。”**

因此，本文更新上一轮按硬件协议能力列出的功能顺序：当前最值得验证的是「首次设置后，日常打开 App 即自动同步，处理期间无需盯守」，遥控录音、增益设置和完整设备面板暂缓。自动校时作为已确认问题的修复继续收尾，不应占用新功能探索的主要预算。

采用 sz-mvp 的诊断与设计方法：先写关键假设，找到真实使用者，预先定义成败标准，再用单功能版本验证；不能以功能存在、用户称赞或测试数量替代日常行为证据。

## 1. 从用户最终要完成的事推导价值

当前工作假设是：用户用硬件记录会议、交流等内容，之后在深脑里获取可以回看和使用的记录与分析。具体使用频率、典型时长、等待发生在哪一阶段尚无量化数据，不能编造。

一次成功使用至少需要：

1. 需要保留的声音被完整录下，音质足够使用。
2. 时间、录音身份、归属账号正确。
3. 音频从设备完整到达手机，能够在中断后继续。
4. 所需内容被提交并处理，结果可打开。
5. 用户付出的操作、盯守和排查成本足够低，愿意下次继续使用。

录音丢失、错账号、错误的“完成”提示是底线，不能用少几次点击交换。底线之上，本轮主要优化第 5 项，而不是扩充控制命令数量。

硬件按键的潜在价值是让录制独立于手机界面。把每次录制都改成“解锁手机 → 找 App → 连设备 → 点开始”，可能增加操作；只有设备难以够到等真实场景才能证明遥控的增量价值。

## 2. “操作和等待”需要拆成四种成本

| 成本 | 典型表现 | 优先策略 |
|---|---|---|
| 重复操作 | 找设备、选设备、再次点同步、反复重试或刷新 | 记住已选设备和账号，日常自动触发与恢复，保留明确暂停入口 |
| 必须盯守的时间 | 不敢锁屏或切 App，怕任务丢；必须等完才能做别的 | 验证持久化恢复和后台传输，安全落盘后清楚提示，正常处理不要求停留 |
| 实际处理时延 | BLE 传输、上传、云端处理耗时 | 分阶段测量，再优化握手、排队、冗余传输或服务端瓶颈 |
| 不确定性 | 不知道录音在哪、是否已保存、是否需要再操作 | 用可验证状态说明“已保存到手机 / 待传云端 / 正在处理 / 结果可查看 / 需你处理” |

必须分别记录总耗时与主动等待时间。传输耗时不变但用户可以安心离开，是有价值的改善；只让进度条更流畅、不改变实际盯守和结果时延，不算主要问题被解决。若用户需要立刻使用结果，总时延本身仍必须优化。

最终目标可以是「日常只操作硬件，结果自动到手机」。第一段先验证「打开一次 App 后零额外操作」，清楚保留这一步，不把它宣传成完全不用打开 App。

## 3. 当前证据与未知项

### 已确认

- 用户直接报告时间错误，以及反复操作和等待的负担。这是需求证据，但不是点击数或等待分钟数的测量。
- `AppModel.selectedDeviceId` 是内存状态；已有 `syncIntent.<ownerKey>` 用于未完成任务恢复，成功完成后会删除。
- `sceneChanged` 恢复的是既有同步意图；没有一个持久的首选设备偏好，在完成上一轮后自动查找下一轮新录音。
- 手动扫描设置为 6 秒；设备信息查询串行执行。6 秒是代码配置，不等于每次用户实测总等待时间；各查询的超时上限也不是典型耗时。
- 已实现增量跳过已完整保存文件、下载检查点、重连续传、独立后台上传、有限重试和前台结果对账。应复用并验证，不能将它们重复列作全新功能。
- 现有真机记录证明一次 4,109,400 字节下载经历约 30 秒锁屏后完整完成并匹配哈希；该轮没有实际掉线。掉线续传、新录音后台上传收尾、系统终止等仍有验收缺口。
- 自动校时代码已完成协议测试，但尚未在手机新版和硬件显示上验收。

### 必须验证，不能先当成事实

- 录音保存后，硬件是否无需额外按键就保持可发现/可连接；若固件休眠后不响应，App 不能仅靠记住 UUID 保证唤醒。
- 用户最耗时的是连上前、下载、上传、云端处理，还是反复确认状态。
- 手机放口袋、锁屏、切 App、暂时离开设备后的恢复是否稳定。
- 是否经常有多条历史录音排队，导致刚结束的会议迟迟不能查看。
- 是否存在收音不清、够不到硬件按钮、经常空间不足等问题；目前没有用户证据支持将这些提前。

## 4. 重新排序

优先级依据：对本次实际痛点的直接作用、证据强度、可减少的日常负担、实现与长期维护成本、潜在副作用。缺少使用频次和时延基线，故不提供伪精确的收益评分或工期。严重的数据正确性问题是发布门槛，不参加普通功能加权排名。

| 优化 | 当前判断 | 最小实现或验证 | 升级/停止条件 |
|---|---|---|---|
| 记住设备与账号，打开 App 自动查新录音 | **主 MVP，最高优先**；直接减少每次的操作 | 一个账号范围内记住一台用户选定设备；开启自动同步后，前台进入时优先续传，再做一次有界查新；优先使用系统已知设备，必要时才扫描 | 真机可无额外按键连接；常规使用不再进入设备页操作。若硬件不可被唤醒，先处理这一约束 |
| 切 App 后可继续或可靠恢复 | **同一 MVP 的发布门槛**；减少盯守 | 复用已做的检查点和后台上传，补真实掉线、弱网、重启和收尾验证，修复被复现的缺口 | 进度保留、非零 offset 续传、内容一致、云端会话不重复；失败先修复，不叠加新功能 |
| 明确保存/处理状态，正常流程不要求刷新 | **主 MVP 的必要反馈**；减少“我还要不要等” | 在记录页给出当前任务简短状态、最近一次检查时间和真正需要操作的异常；自动取回结果 | 用户能说清录音在哪、下一步是否需要自己操作；不把写入/上传/分析混成一个完成 |
| 自动校时 | **完成现有修复**；已知问题、改动小 | 安装验收首次连接、重连、重启后的显示与新文件名 | 写入无回执，不展示未经确认的“硬件已校准”；不批量推测修正旧录音日期 |
| 优化连接到开始下载的时间 | **测量后做的小优化** | 分解扫描/连接/服务发现/元信息/列表耗时；若固件版本等非关键查询阻塞明显，缓存或延后 | 以实测收益决定；录音状态等用于完整性判断的查询不能直接删除，也不能在当前队列上盲目并发 |
| 最近需要的会议优先得到结果 | **条件性第二优先**；针对真实排队等待 | 在已知时间可信的前提下排序；保留正在续传任务和已完成跳过，允许用户一次性“优先这一条” | 若没有积压，收益有限。时间不可信不能自动排序并排除文件；第一版不要求用户每次手选 |
| 不打开 App 的后台自动发现新录音 | **第二段核心实验**；可能进一步消除最后一步 | 在第一段验证通过后，测试后台发现、状态恢复、硬件保存事件和有限会话策略 | 同时满足结果可达、耗电可接受、不持续争用设备。不能以后台模式声明承诺永远在线 |
| 真正的结果就绪通知 | **条件性第二段**；减少反复查看 | 前台已观察到完成可更新界面；App 不运行时的云端完成通知需要独立推送机制 | 先确认有没有频繁回来查结果；不能用定时本地通知假装云端已经完成 |
| 低电/空间异常提示 | **轻量辅助**；不另建完整仪表盘 | 连接时利用已取得电量；容量先验证合理性和比例，异常才突出 | 若经常发生录音中断/空间满，升为重点；无证据时不加会前必做检查步骤 |
| 手机遥控开始/暂停/保存 | **暂缓** | 用上游现有能力做一次真实场景对照，比较硬件按键与手机操作成本 | 仅在频繁够不到设备、硬件按钮难操作等情况下提前 |
| 拾音增益设置 | **先实录实验，暂不做产品界面** | 固定声源、距离与摆位，对比三档的可懂度、失真和转写效果 | 实测默认档明显影响可用结果才做；如果一个默认档已足够，不把选择负担交给用户 |
| 按键与 App 长时间实时联动 | **不作为首个 MVP 前置** | 首先只验证所需状态是否可查询；第二段按键事件驱动查新时再补事件分发 | 不能为了状态动画先改造为持续占用设备的系统 |
| 安全清理/完整设备文件管理 | **出现空间痛点后再做** | 先统计和展示已备份副本，逐条可确认清理；已知固件适配与重拉列表必须保留 | 不开启自动删除以换取“少操作”；当前尚有恢复验收缺口，原始副本仍重要 |
| 实时字幕、波形、片段预听 | **暂缓独立探索** | 先验证现场必须看文字或预听才能选文件的需求，再做受控单场景原型 | 对本次日常同步摩擦没有直接证据；实时 ASR 和流式音频不能夹带进入自动同步版本 |

## 5. 主 MVP：打开 App，录音自己回来

### 要验证的关键假设

在用户已经选定设备、账号和自动同步偏好的情况下，录音后打开 App 即自动发现并带回已结束的新录音，允许用户切走；这能显著减少其额外操作和主动等待，而不会增加漏录音、错误归属、重复任务或设备争用。

这里验证的是行为改善，不只是“自动连接 API 调用成功”。

### 首次设置与日常路径

首次：选择自己的设备，确认同步账号与自动同步偏好。历史录音首次导入单独记账，不能混入日常增量同步指标。

日常：

**用硬件录制并保存 → 打开 App → 自动识别、校时和查新 → 继续使用其他 App → 返回查看结果。**

打开后的正常路径不要求再次选择设备、点击同步、逐条点击上传或反复刷新。需要等待硬件靠近、网络恢复时保留任务，状态解释原因。蓝牙未开启、登录失效等确需人处理的情形才给出单一明确操作。

保留手动同步作为故障和特殊场景入口，但不能让它继续成为自动模式的必经步骤。

### 第一版具体边界

- 一个账号范围内一台首选设备；保存本机 CoreBluetooth 标识，不把同名 CB08 或最强信号当成用户设备，不使用未经证实唯一性的授权码代替设备身份。
- 持久的自动同步偏好、当前任务恢复意图、用户主动暂停必须分开。不能简单不删除 `syncIntent`：否则会混淆已完成任务与下一次任务，也可能让暂停后再次打开就被偷偷重启。
- 前台进入时合并重复触发；同一时刻一个 BLE 同步任务。有界连接/扫描、失败退避、必要的冷却，不在每次切 tab 时重新连接。
- 优先续传未完成文件，跳过已完整落盘内容，再获取新录音。新旧识别不能仅依赖日期大于“上次同步时间”，因为已知硬件时钟有问题。
- 当前仍在录制的文件不能按已结束文件上传；状态不明时保留待同步，不把跳过解释成全部完成。
- 沿用既有上传和分析规则及账号隔离；自动触发不等于放开重复建会话或重复启动收费分析。
- 下载结束释放硬件，云端上传继续。使用“连接做完一轮就释放”的方式验证主假设，无需一开始改成全天长连接。
- 用户显式暂停优先于自动恢复；按账号隔离暂停状态，只有明确恢复才继续，不因前台事件覆盖用户选择。
- 本轮只需串行命令，不必先重写整个 BLE 协议引擎。若发现具体通知丢失影响当前流程则定点修复；实时遥控/音频/按键并发另行需要统一消息分发。

### 最小的状态表达

| 状态 | 用户应当明白的事 |
|---|---|
| 正在从灵魂卡取回 | 当前仍依赖蓝牙范围；离开设备可能暂停，已保存进度保留 |
| 已保存到手机，等待网络/正在上传 | 本地完整副本已确认，无需维持硬件连接 |
| 云端正在处理 | 文件已提交；不需要重新上传或守着设备页 |
| 结果可查看 | 当前结果实际已返回，点击可打开；转写与分析分别如实标注 |
| 需要处理 | 明确原因与一个下一步；普通等待/后台暂停不冒充不可恢复失败 |

不要在蓝牙正在取回尚未完整的数据时提示“录音已安全保存”。不要承诺离开蓝牙范围还能继续传；目标是中断不丢进度且稍后可接续。

## 6. 用最小代价验证，而不是一次把全部做完

### 步骤 A：先确认最可能推翻方案的硬件条件

使用专用短测试录音，在保存后不再触碰硬件，尝试通过已知设备连接；分别观察待机、锁屏、离开后返回、被其他客户端占用的情况。确认平常录音结束后的设备可达性，再决定自动发现策略。若连接必须额外唤醒，记录最少可行的人机动作，不把 App 界面包装当成固件能力。

同时将自动校时修复做真机验收：首次连接、重连、开关机后显示，新录音文件名和播放时长正常。校时前已产生的旧日期保留来源；校时/RTC 重置导致重名是否可能发生要验证，不能宣称已发现重名数据丢失。

### 步骤 B：记录短基线，不要求用户回忆精确分钟

后续 3–5 次实际使用，记录：打开 App 后为同步做的额外操作、为了盯任务停留的时间、首条完整本地文件时间、首个可用结果时间、等待原因、是否中断。尽量复用已有诊断事件；主观盯守时间可用简单使用记录补充，不能从前台时长直接等同计算。

### 步骤 C：只交付上述单功能版本

复用当前下载、上传、对账能力，增加持久设备偏好与有界前台查新。沿用当前阅读页，不夹带遥控、增益、多设备中心或长连接改造。真实硬件、真实传输和真实结果必须跑通，不能用假进度/人工代同步证明可靠性。

### 步骤 D：真实日常试用与受控故障分开记录

先由当前用户试用连续 10 次自然录音同步机会，另用测试录音验证掉线、弱网/断网、切 App/锁屏、重新启动、主动暂停和账号切换。各阶段比较相近时长、大小与网络条件，不能把短文件新版本与长文件旧版本直接做速度结论。

以下是**事先建议的继续/停止门槛，不是已测结果或行业标准**：

- 10 次自然使用中，至少 9 次在已开启自动同步、账号有效、设备可连接的条件下，打开 App 后无需额外同步操作；同时报告所有录音机会及不满足条件的次数和原因，不隐藏难例。
- 主动等待时间的中位数相对基线至少降低一半；若基线已经接近零，则以额外操作数和用户反复确认次数为主，不以无意义百分比宣称收益。
- 每场额外操作数为 0 是正常路径目标，计数不包含首次设置，但“打开 App”本身单独记为 1 次必要动作，不能宣称用户完全无操作。
- 受控中断后检查非零偏移恢复和最终完整内容；重启后任务仍可找回，云端不重复建会话。出现丢失、错账号、错误完成或不可解码文件立即停止扩展并修复。
- 用户在有手动入口可选的情况下，连续自然选择自动模式，不因为不信任而反复进入设备页检查。试用后询问仍在等待的具体阶段。

10 次、单个用户只能判断这次改动有没有方向性价值，不能证明长期可靠率或市场适用性。受控故障试验通过也不能替代系统终止的真实场景验证；必须区分系统回收进程与用户主动强退。

### 三色判断

- **绿灯：** 操作和盯守明显下降、硬性正确性检查通过，继续第二段实验。
- **黄灯：** 自动流程能跑，但仍总回来看进度；优先查状态可信度、真实总时延或后台收尾，不立即添加新按钮。
- **红灯：** 频繁需要手动重连、用户不敢离开、任务错误或状态误报；先修底层条件，停止扩展其他能力。

## 7. 第一段通过后，第二段如何选

只按剩余的最大阻碍选择下一项：

- 用户仍嫌需要打开 App → 验证后台发现/硬件保存事件触发，从一次打开进一步减少动作。
- 用户反复回来查是否完成 → 验证真实结果推送和可点击直达，不用定时通知猜完成。
- 用户急着查看刚结束的会议，但排在旧录音后 → 验证优先队列，并测首个可用结果时延。
- 每次连接后长时间不开始下载 → 优化实测阻塞的握手/元信息步骤。
- 录音内容本身不清楚 → 用固定条件实录对比增益，先找合适默认设置。
- 频繁存储满 → 接入经过副本确认的清理能力。

第二段不要求新增功能全部上线。若要从当前个人验证推广为产品，再找 3–5 位相似用户观察重复使用；商业验证应看真实试用后是否续用/付费，而不是对“自动同步”概念表示喜欢。基础缺陷修复无需包装成单独收费卖点。

## 8. 平台边界与成本

Apple 文档明确指出，后台蓝牙可以通过事件及状态恢复支持长时任务，但后台模式不保证无限执行，后台扫描与前台行为不同。因此第一段承诺「打开自动开始、受限时可靠恢复」；第二段用真机证明更强的后台能力。不能用持续高频扫描或保持页面常亮来掩盖任务恢复不足。

自动化也有代价：不必要的重连会增加耗电、占用设备并与 Mac 等客户端争用。应检查实际新文件、有限重试、完成即释放；自动查新没有新内容时安静收尾。已读设备状态应标明是否来自当前连接或上次读取。

不要以“提速”为由放宽完整字节校验、跳过录音中状态检查、将分段音频当成完整文件，或把 iOS 不能保证的常驻行为写进用户承诺。
