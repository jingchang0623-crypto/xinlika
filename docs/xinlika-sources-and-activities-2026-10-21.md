# 声音归属、场景与活动归集

后续 r10 已上线新封批自动声音任务及本人登记，见 [全天标签与声纹实测](xinlika-allday-voice-2026-10-21.md)。下文保留 r8 当时的实现与边界。

用户指出的两类问题是主链路问题：持续录音里并非所有声音都属于用户，真实生活也不按一分钟分成事项。本轮分别处理“声音证据”和“活动组织”，不让声纹或音频分包独自决定用户经历。

## 三种判断不能混为一谈

| 判断 | 能提供什么 | 不能直接推出什么 |
| --- | --- | --- |
| VAD／声音标签 | 语音区间、音乐和环境声等候选线索 | 有语音不代表用户说话，室内语音不代表现场交流 |
| 说话人区分／声纹比对 | 匿名说话人片段；登记后与本人声音的相似度 | Speaker 1 不是用户；相似本人声音也可能来自播放或会议回声 |
| Agent 场景与语义理解 | 综合录制时间、声音线索、明确会议上下文及讨论变化，形成活动和事项 | 不能只凭关键词猜午饭、地铁、本人承诺或真实会议边界 |

视频会议的远端发言可能是重要上下文，应保留为他人观点／会议决定。音乐、视频和公交报站不应写成用户经历。通勤中的用户口述又应单独保留，不能把整段“有交通噪声”的录音全部过滤。未知归属保持未知，普通记录仍自动整理，不要求逐条确认。

## 开源声音方案及本机实测

实际复用 [sherpa-onnx](https://github.com/k2-fsa/sherpa-onnx/blob/a63f82130d91d99a23a43f346104706881b31ff1/README.md) 的 Python／ONNX API：Silero VAD、Zipformer-small 音频标签及中文 WeSpeaker embedding。官方实现支持说话人识别／区分、声音标签和 VAD，并提供 iOS、macOS 等端的接口。参考 [声音标签示例](https://github.com/k2-fsa/sherpa-onnx/blob/a63f82130d91d99a23a43f346104706881b31ff1/python-api-examples/audio-tagging-from-a-file.py)、[说话人示例](https://github.com/k2-fsa/sherpa-onnx/blob/a63f82130d91d99a23a43f346104706881b31ff1/python-api-examples/speaker-identification.py)。[3D-Speaker CAM++](https://github.com/modelscope/3D-Speaker/blob/065629c313eaf1a01c65c640c46d77e61e9607b4/egs/3dspeaker/sv-cam++/README.md) 是后续可比较的声纹模型，本轮没有假称已验证它。

新增 `scripts/probe-xinlika-acoustics.py`，只读取显式选择的 1–300 秒本机音频，不连接录音卡、不调用 ASR。已有授权的真实会议片段 59.28 秒和用户确认的背景视频片段 20 秒均实际运行了三个模型。

两个样本都出现“语音、室内”等标签；会议还出现“独白”标签。这直接说明仅靠 VAD 或标签不能可靠区分会议与播放。两者各得到一个匿名分簇，也不能据此认定是一名真实说话人或用户本人：当前采用粗粒度五秒窗口，不是重叠语音的精确轮次分离，示例相似度阈值未做现场标定。

背景片段的 Mac 峰值 RSS 约 369 MB；不能将该数字当 Linux／iPhone 内存或全天耗电结论。因此本轮声音模型只在隔离本机环境运行，未塞进现有 768 MiB 云端主容器，未启用自动丢弃、跳过转写或本人归属。原声和匿名 embedding 均留在忽略的 `.build`。

尚缺一次干净的本人声纹登记及公交／地铁、音乐、会议、视频的现场对照。必须验证误认和漏认，而不是直接采用网上的相似度阈值。重放／声道差异也需要单独测试。当前生产仍使用已实现的来源过滤和“录音中的讨论”归属边界。

## 标签如何进入实际分析

新增 `heartball_audio_context.py`，把声音观察作为独立旁路证据保存到 SQLite。每份观察绑定原始 CB08 批次哈希、选择区间、模型与标签表哈希、生产器版本；完整标签及分数持久保存，给模型的上下文有抽样和长度上限，并明确未展示窗口不能视为静音。匿名说话人标签只在该份观察内有效，不跨录音认人。重点片段沿用原声批次，标明可能包含边界上下文，不冒充逐字声纹对齐。

导入要求哈希匹配已有授权批次，区间不超过原声、分数有效、本人身份保持未登记、播放来源保持未知。相同模型和区间重复导入幂等；不同结果不能静默覆盖。撤销处理授权后不再进入模型上下文。标签本身不修改来源策略、文字或个人事实，不建立新的 ASR 任务。

新记录抽取、语义整理、活动归集、Personal Agent 均能接收辅助声音观察。观察到达会使活动／Agent 的上下文指纹变化，复用已有转写重新分析；已整理的历史事项不因补充标签而重跑 ASR。活动上下文按观察身份去重，避免一个批次有多个议题时把相同标签大量重复发送。

本轮另从已授权云端备份选取两段各 60 秒的真实批次，在本机运行声音模型：分别得到 0／14 个 VAD 区间、0／2 个匿名分簇。其中前一段 6 个窗口中有 5 个的最高标签为 Speech，却没有 VAD 区间，保留该分歧，不能据此宣称静音或有可辨认语句。该数字只是模型产物，不是静音准确率、真实人数或本人识别成绩。仅将 JSON 观察送回云端，没有重复上传原声。生产上下文已读到两份观察，Personal Agent 最近记录中的一条带观察；真实模型归集和静默观察均已完成。来源策略及原转写／文档／事实数量不变，ASR 仍为原有 22 项。

**当前是显式选择片段的声音模型验证＋已接通的标签消费链路。全天自动打标签的生产任务、本人登记和播放声可靠分类尚未上线。** 暂不把声音模型放入现有主处理容器，避免未测量的内存开销影响采集后的主处理。

## 活动、事项、主题三个层次

以下是展示结构示例，不是本轮实测的午饭或周会：

```text
今天
  午饭闲聊 12:00–12:30
    交流摘要；展开具体事项和重点
  项目讨论 14:00–15:00
    方案、决定、下一步
  周会 15:30–18:00
    多个项目议题；仍属于同一场会议

项目主题
  跨上面的活动、跨日期关联同一个持续目标
```

新增 `heartball_activities.py`：在语义事件之上自动生成有标题、概括和来源范围的活动容器。不是按文件或时长硬切；同一录音可以有多段活动，一场长会议可以容纳多个议题。显式相同会议身份不得拆成互不相干的活动；不同会议／来源不能随意混合。重点继续作为独立结果，能够唯一定位时归入对应活动。

活动投影不合并／删除原事件，也不改跨日期主题。引用漏项、交错、编造或改版会被校验拦下。用户纠正导致依据失效时重新归集；同一语义事件追加内容允许更新投影，避免持续录音时永远无法发布。活动身份以首个依据事件保持稳定，后续追加议题不会每次折叠已展开卡片。

时间由录制来源计算，展示的是**可观测来源范围**。采样片段跨两个半小时，不代表采满两个半小时，也不证明会议恰好在两端开始结束。服务端另保留去重后的已观测音频秒数，缺口不补成零丢失；没有可靠录制时间的事项不使用处理时间补齐。

活动和 Personal Agent 使用独立上下文队列及检查点，避免慢模型分析阻塞主 ASR 队列。默认五分钟归集；音频仍默认一分钟封批，最长五分钟。新增上下文任务也支持原有鉴权重试接口。

## 本轮验证与交付边界

- 138 项 Python 测试、60 项 Core 自测通过；Mac 与 iPhone 构建通过。控制测试使用合成数据，不作为活动识别质量。
- 真实授权会议账本＋现有模型的隔离验证：15 个事项、2 段重点归为 3 个活动（1 个会议、2 个对话），原事件不合并，不调用新 ASR。活动名称与边界准确率尚未人工验收。
- 云端升级到 r8；原 r7 停止保留，其他容器不变，升级前完成账本和已封批原声备份并检查没有进行中的采集／处理任务。r5 的真实归集曾被结果校验拦下；r6 增加私有诊断并修正“重叠来源范围不等于真实议题交错”的校验后，真实归集首轮完成。r7 另修正不同时区 ISO 字符串排序问题，始终按录制时刻排序。带两份声音观察的真实生产归集完成（13 个事项归入 4 段活动，重试一次）；Agent 接收标签及活动后安静归档。r8 增加具体交错位置的纠错反馈，保留校验规则。活动边界准确性仍未人工验收。正式结果见 [validation](validation/xinlika-sources-activities-2026-10-21/result.json)。
- 客户端源码显示活动标题、时间范围和短概括，展开事项和重点；旧客户端仍能读取活动标题与分组。Mac 0.4.5 预览包已打包，未替换正在运行的 App；iPhone 本轮只构建，未安装或启动新录音。
- 当前自动活动分析范围为 Asia/Shanghai 的当日、最多 100 个有效语义事项；超出明确标为 `limited`，保留今天全量事项和原分组，不截断页面，不阻断 ASR。更大规模的分层滚动归集和多时区调度尚未实现。

本轮没有新增录音、改变硬件模式、登记本人声纹或把未知声音升级为个人记忆。声音来源完整闭环仍需后续真机与资源验证，不宣称已经达到全天可靠区分的效果。
