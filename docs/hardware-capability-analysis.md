# 录音笔硬件能力与 App 功能建议

日期：2026-09-06。本轮为研究和产品建议，未接入下列新功能，未操作真实录音笔。

后续更新：用户明确反馈“硬件和 APP 互动太麻烦了，每次都要操作和等待”。本文继续作为技术能力清单；下述原始优先级已由[第一性原理与 MVP 决策](hardware-mvp-priorities.md)更新，当前优先验证设备记忆、打开 App 自动同步与无需盯守的恢复链路，遥控和增益设置暂缓。

## 结论

硬件协议可支持独立设备检查、遥控录音、增益设置、按键联动、文件管理和实时音频。结合后续真实反馈，下一版优先验证「首次记住设备 → 打开 App 自动查新与同步 → 中断可恢复 → 返回即可查看已就绪结果」。下表保留最初的能力评估顺序作为研究记录，实施优先级以 MVP 决策文件为准。实时音频应作为独立探索，不应将现有离线转写误认为完整的实时字幕方案。

参考仓库当前 master 为提交 `ac762fea4cb3372fa87d0739310796f216902a23`。依据是公开协议、Python 设备层、Web 控制入口及模拟测试；没有把“有命令和实现”当作“用户这台固件已验证”。上游文档列出的真机验证重点是连接、电量、列表、WAV 下载、CRC 和文件结构，不能据此声称全部录音控制和并发行为均验证通过。

## 当前 iOS App 的实际起点

- 自动校时已加入共用 BLE 核心，尚待新版手机安装和硬件屏幕验收。
- iOS 展示电量（含充电状态）、固件、扫描时信号、文件数量、下载进度和云端状态。
- 共用核心已有容量、增益、录音状态和当前文件名查询；iOS 使用状态/文件名跳过正在录制的文件，没有完整录音控制面板。
- iOS 已有下载检查点、重连续传、完整字节数校验、落盘哈希和独立云端上传，不需要重做这些能力。
- 当前入口是登录后的「连接并同步」，同步结束会断开；暂停下载也会断开。要持续显示设备状态和响应机身按键，需增加独立的设备连接会话。
- Mac 已有低电量提醒、设备与账号绑定、可选的同步后清理；iOS 没有接入这些完整功能。跨平台可复用判断原则，不能直接复用不同平台的本地账本。

## 建议能力清单

| 功能 | 对用户的改善 | 协议与现状 | 优先级与验证 |
|---|---|---|---|
| 独立连接与会前检查 | 无需登录云端也能连接、校时、看电量/充电、存储占比、当前录音状态和时长；低电/低空间有明确提示 | 容量 `0-1/2`，电量 `0-3/4`，状态 `3-19/20`，时长和当前大小 `3-21/22`。已有多项查询，需独立连接和状态展示 | 第一批。容量先校验原始值与比例，绝对容量和剩余录音时长需实测标定 |
| 手机遥控录音 | 录音笔放桌上，从手机开始、暂停、继续和结束保存；显示硬件确认的状态与时长 | `3-1/2` 开始、`3-3/4` 保存、`3-5/6` 暂停、`3-7/8` 继续；上游设备层和 Web 层均有调用 | 第一批。每个操作验证应答及状态，超时后先查询，避免盲目重复开始/保存 |
| 拾音增益设置 | 在 App 选择低/中/高三档，改善不同距离的收音适配 | `3-25/26` 查询，`3-27/28` 设置；现有核心只有查询 | 第一批。设置后读回，实录比较效果，验证重启后是否保持。只承诺增益，不称为降噪或麦克风模式 |
| 机身按键联动 | 按硬件开始/暂停/保存，App 跟随显示；保存完成后刷新列表，将新录音加入既有同步队列 | AE23 按键/状态通知，上游有设备事件回调。当前已订阅但没有独立事件分发 | 第二批，可和遥控状态层一起打基础。校验事件含义、重复/乱序和录音保存完成时机；不能仅收到按钮事件就下载未完成文件 |
| 设备录音库与选择同步 | 浏览硬件上的录音，区分待同步、手机已保存、云端已确认；优先同步用户选中的会议 | `2-0/1/18` 文件列表、`2-2` 下载；列表和下载已实现，主要补选择、队列排序和状态投影 | 第二批。保留既有断点与完整性判据；列表不完整时明确提示，不能误判设备文件已经不存在 |
| 清理已经备份的录音 | 查看可释放空间，选择删除已完整保存并确认云端归档的硬件副本 | `2-8/13` 单文件删除；共用 Swift 实现已有实际固件适配，Mac 有清理判据，iOS 尚未接入 | 第二批。先做用户确认的逐条/批量选中清理；排除录音中或状态不明的文件，删除后重拉列表确认。无需引入删除全部 |
| 暂停传输但保持设备连接 | 暂停大文件下载后仍可查看设备和控制录音，再从断点继续；展示传输速度和估算剩余时间 | `2-7/11` 终止当前导入，已有 offset 续传；当前暂停通过断开连接实现 | 第二批。协议没有独立“冻结传输”命令，应实现终止本轮＋持久化检查点＋以后续传；验证停止后的在途分片如何收尾 |
| 短片段预听 | 同步长录音前先确认内容是否是想要的会议 | `2-12` 按字节范围下载，上游有模拟测试；当前只有构帧方法 | 探索项。字节范围并不直接等于秒数，需验证 OPUS 包边界、起止范围语义、封装和解码。不能将片段登记为完整录音 |
| 边录边看文字/收音反馈 | 用硬件收音，手机实时显示文本；后续可以增加真实电平或波形 | `1-0/1/2/3/4` 控制实时 OPUS 推流及状态；上游主要保存音频码流并显示字节/事件 | 后续独立项目。需音频解码、流式 ASR、断流恢复和持久化；并发录音、推流与下载、锁屏行为均需单独验证 |

## 必须先补的工程基础

**统一蓝牙消息分发和设备会话状态。** 现有 `BLEClient.expect` 从共享队列取帧，不匹配的帧不会交还；iOS 下载循环也会跳过非文件类型。这适合串行执行的同步任务，但不能直接再加一个电量轮询和按键消费者。应由单一入口接收并按请求应答、文件会话、实时音频和设备事件分发；相同应答类型的请求串行化，保留 AE22/AE23 各自的半帧缓冲。上游 `_handle_frame` 的分类分发可参考，不能未经检验假设其所有并发情况都已完备。

**设备连接独立于云端上传。** 当前 `syncSelected` 要求登录，`startSync` 在结束时断连。建议建立设备会话供校时、查询、遥控共用；云端上传继续沿用账号隔离与账本规则。纯设备控制不应依赖登录或网络。长连接的耗电、与电脑争用和恢复行为需真机评估，不能把前台可用推广成后台永久在线。

**结果码按命令解释。** 录音开始/保存/暂停/继续是 `1` 成功、`2` 失败；增益设置是 `0` 成功、`1` 失败。不要共用一个“非零即失败”的判断。遥控动作先显示处理中，以应答和回查决定最终状态；状态未知不显示为待机。

## 两处上游不能直接照搬

1. **容量单位存在冲突。** 厂商文档标 8KB，上游按 1KB，本地 Swift 注释记录真机更接近 64B。优先显示经过合理性校验的剩余/总量比例；校准前不承诺具体 GB 或“还能录 X 小时”。电池百分比也不足以推算剩余续航。
2. **删除参数与用户固件实测不一致。** 上游仍发送文件列表的 28B 原条目；本地 Swift 已记录 CB08/V1.0.0 在 2026-08-28 的实验，使用 `offset:4B LE + filename:24B`。应保留现有适配和删除后重拉列表的确认。上游删除超时仅返回无应答，不能作为成功依据。

## 尚无足够依据承诺的功能

在本项目公开命令表中未找到 OTA 固件升级、蜂鸣寻找设备、定位、屏幕亮度/显示样式、硬件蓝牙名称修改、录音降噪模式、采样率/码率切换或设备端定时录音接口。它们需要厂商协议补充或固件支持，不能仅靠这个仓库保证实现。App 内的设备昵称是本地显示名，不代表更改了硬件广播名。

项目能读取授权码，但没有证明该值是跨手机、跨电脑稳定且唯一的设备序列号，因此暂不能用来保证跨端设备绑定。可先增加本地设备昵称与账号归属确认；固件版本查询可用于诊断，但查询版本不等于可以升级固件。

## 建议下一版的完成标准

先覆盖待机 → 开始 → 暂停 → 继续 → 保存的完整状态循环，并在同一连接下验证机身按钮与手机操作互相可见；录音中断连后重新连接能够恢复真实状态。增益写入可读回、实录可比较。下载发生时不会丢掉状态事件，也不会因查询电量损失文件数据。容量读数未标定前仅展示有效比例。

本次建议不意味着功能已经实现；下一轮实际接入应使用专用短测试录音验证控制和清理，再回归既有长录音断点下载。
