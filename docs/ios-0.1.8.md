# 0.1.8 (9)：修复 CB08 的 App 录音控制

## 原因与修复

用户测试的 CB08 / V1.0.0 不执行此前采用的 `TYPE=3 CMD=1/3` 录音控制。0.1.7 的两次真实开始操作均没有命令应答，连续状态查询仍返回未录音。详见 [0.1.7 诊断](ios-0.1.7.md)。

根据上游 [协议](https://github.com/lomehong/record/blob/master/docs/协议.md)，改用另一组 App → 设备命令：

| 操作 | 命令 | 确认依据 |
| --- | --- | --- |
| 开始录音 | `TYPE=1 CMD=0`，空参数 | `3-19 → 3-20 state=1` |
| 结束并保存 | `TYPE=1 CMD=2`，空参数 | `3-19 → 3-20 state=2` |
| 状态、时长 | 保持 `3-19/20`、`3-21/22` | 设备实际返回值 |

开始回包是文件名，结束可能没有应答，不能套用布尔成功码。控制与查询现在分开：新鲜状态检查 → 只发送一次控制 → 只读轮询确认。不会因缺少应答重发，也不会自动回退到其他控制命令。暂时缺失一次状态回包可以继续查询，始终无法确认时仍显示待确认。

实时 OPUS 通知 `1-1` 会在接收时丢弃，不进入等待队列、日志或本地文件。开始确认后释放这条实时连接，后续监控重新建立只读连接。断连后录音是否持续，已由实际卡上同一文件的时长与保存结果验证；不以蓝牙写入成功代替硬件验证。

界面保留“开始录音”“结束并保存”及必要状态。同步暂停、导入确认、长录音拦截和上传开关仍由原有流程控制。诊断入口只在 Debug 且显式指定目标 UUID 时运行，Release 不提供自动探测入口。

## 真机证据

2026-09-07 12:52，iPhone 16 Pro 连接 CB08 / V1.0.0：从未录音开始，状态变为录音；断开、重连后文件身份不变，时长 7 秒；发送停止后变为未录音，文件列表中确认保存了 7 秒 / 14,400 字节文件。见 [第一轮协议实测](validation/ios-0.1.8/hardware-type1-baseline.json)。

12:59 的第二轮使用正式 `RecordingControl.perform` 和 `BLEClient.sendRecording`，开始、保存均读回确认成功。额外尝试暂停时发现固件限制：发送 `1-3 parameter=1` 后时长停在 2 秒，但 `3-20` 仍返回 1。整轮包含的暂停验收未通过，原始报告保留 `success=false`，没有改写为全通过。见 [暂停限制证据](validation/ios-0.1.8/hardware-pause-limitation.json)。

因此本轮不开放暂停、继续录音按钮；不能保证该固件查询能区分录音与暂停。状态 1 表示录音会话尚未结束，不能仅凭它证明音频仍在持续写入。结束并保存已在上述时长停止的会话中执行成功。

13:10 最后一轮不包含暂停，正式控制完整通过：开始后状态 1；断开、重连后同一文件继续录制至 10 秒；停止后状态 2，列表确认 10 秒 / 20,600 字节文件。开始阶段丢弃了 31 帧实时音频，重连后的 2 秒观察窗口内收到 0 帧，说明此次重新连接没有继续实时音频推送。见 [正式控制硬件记录](validation/ios-0.1.8/hardware-production.json)。这不等于长期耗电测试。

验证共产生 3 条短测试录音（7 秒、2 秒、10 秒），没有下载音频、调用深脑分析或删除文件。两次中途连接超时均发生在发送控制命令之前；设备重新就绪后才执行下一轮。读回手机偏好确认原有“暂停同步”仍然开启。
