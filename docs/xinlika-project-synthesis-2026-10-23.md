## 2. 产品最核心的定义

**心力卡是基于随身声音上下文的 Personal Agent 项目：持续记录与主动重点共存，自动理解事项、维护主题进展、在有用时给反馈，并能根据纠正更新后续判断。**

硬件是入口，ASR 是中间步骤，记忆库是支撑，MCP 是外部使用通道。真正闭环是：持续感知 → 有来源的事件 → 当前个人处境/目标/主题 → 介入判断 → 有依据的反馈 → 用户纠正/实际结果 → 更新后续理解。

用户曾多次明确纠偏：

1. 目标已从“升级深脑”变为基于现有工程建设开源心力球方向的新产品，正式名为“心力卡”。
2. 不能停在调研、方案或采集原型，要跑真实硬件—App—服务端闭环；优先复用开源方案。
3. 普通记录自动整理，不逐条确认；AI 应负责理解，而不是把候选事实和审核队列放到首屏。
4. 界面简洁，今天显示当天所有已整理内容，按录制时间，不按处理时间。
5. 一分钟只是传输批次，不能每分钟生成一个主题或一张首页卡。
6. 一场长会议/聚餐包含多个事项；跨场次同一具体目标才是主题。活动、事项、主题、原始批次需要不同层次。
7. 不能把他人、视频、远端会议中的第一人称直接当本人经历、偏好或承诺；保留有价值会议上下文。
8. 停止录音、重启、切换客户端和实机实验服从具体会话归属；保留卡上原声，不通过自动删除或盲目重发开始命令掩盖故障。

“今天不放聊天、聊天与记忆集中”是稳定要求；标签名在记忆和聊天/Agent 间有过调整，后期讨论又统一称 Agent。开源文案应以体验和职责为准，不把临时栏目名当不可变产品规格。

## 3. 两个采集场景，一套共同上下文

持续记录：用户自然生活，录音卡持续保存，手机在可用时接流、封批、上传，服务端自动转写和理解。主动重点：用户明确想记的短想法/位置/承诺，单独身份与范围、优先封尾处理，结束重点不停止全局录音，也不重复创建重叠承诺。

CB08 已测机身亮屏短按保存会结束整条录音。厂商按键回应的多个变体没有把它变成无中断重点键；模式拨动未找到可靠独立事件。因此持续模式采用 App 的重点范围入口，独立机身录音另行处理。不能把心力球的按键语义硬套到录音卡。

卡休眠后 App 未验证能远程唤醒；实际日常方式是用户先启动持续记录，断连卡继续保存，结束后自动核对。无充电全天续航和长期边充边录尚未验收。

## 5. 已有能力与尚未完成

采集可靠性已有：原声先落盘、持久账本、身份/序号/哈希、60秒默认/300秒上限封批、独立重点、网络补传、断连缺口、完整参考的大小/结束码/哈希与唯一字节对齐、跨物理续段关联。接回后续流不代表断连音频自动补发。

最新同文件恢复限定 CB08/V1.0.0、通知订阅/原文件/录音状态/计数核对、等待后每连接单次 `01 01` 接流，收到新音频才显示恢复。两轮范围往返含后台已观测成功；系统强杀、其他固件、多次连续往返不在结论内。[蓝牙恢复记录](xinlika-bluetooth-recovery-2026-10-21.md)

多端服务已有：单用户多设备私有空间、可撤销设备凭据、读写权限、持久修订与快照、文本与来源纠正同步、SQLite一致备份、封存音频对象与隔离恢复。不是公开注册的多租户平台，未完成自动异机备份、保留期和容量告警。[共享服务](xinlika-shared-server-2026-10-21.md)

理解层已有：原文/事件/主题/活动分层，逐字多段引用、录制时间依据、首页event/detail筛选、可逆归并/拆分、来源修订使旧派生结果失效。完全自动活动边界、跨天主题召回、全量历史重整和语义准确率仍需真实对照验收。[最新来源修复](xinlika-source-repair-2026-10-22.md)

Personal Agent 已有：observe/respond/review/publish持久节点，五分钟合并观察，无变化不调用模型，15分钟冷却、24小时最多6条，纠正/撤权/重复抑制。真实文字+实际模型有静默与有效引用证据，但不能据此宣称成长教练或长期建议有用性达标。当前反馈在App内；没有完整外部执行、IM推送或独立目标管理器。[Agent循环](xinlika-personal-agent-2026-10-21.md)

MCP 是外部上下文使用的关键愿景，四天讨论多次提出，但检查当前后端没有已实现的 MCP server。Watch 同样只有方案研究。两者都适合首批贡献方向，不能上首页写“现已支持”。

## 6. 关键实测数字应怎样对外说

| 事实 | 正确解读 |
|---|---|
| 充电Mac长测3小时20分钟 | 不支持“三小时是总时长上限”或“全天电池续航” |
| 75秒服务中断后补传 | 是特定网络故障恢复，不是全链路任何故障都无损 |
| 安静口述7个窗口匹配；视频12个未匹配 | 两个场景的对照计数，不是100%声纹准确率 |
| 餐桌615个粗语音窗口仅2个匹配 | 距离/混声泛化不足，不能简单降低阈值凑成功 |
| 聚餐约22:19–23:15、29个子事项 | 用户时段辅助的活动容器与页面验证，不是无提示自动识别成绩 |
| 270个普通事项+两段重点呈现31行 | 首页层级改善，不能用压低条数证明理解正确 |
| 新补280批，已有408项ASR不重跑 | 幂等与恢复有价值，不是逐字准确性 |
| 17:39–19:53未找到正面覆盖证据 | 仍为未知，不归因静音、没电或固件自停 |

早期ASR会话中的0.43%/0.84%为合成语音字符错误率；后续真实录音15秒/10秒切段的26.36%或40.8%为机器输出差异。两者都不能当真实会议CER/WER。原生开发测试数量也不直接沿用为公开包验证结果。

## 7. 开源复用与取舍

实际运行：LangGraph、SQLite Checkpointer、OpenAI兼容SDK、Pydantic、HTTPX；voxgate为既有语音研究适配器，sherpa-onnx/Silero/Zipformer/WeSpeaker为声音旁路。源码开源许可不等于非公开上游服务授权，模型权重也单独核对。

Omi最值得参考持续感知、来源记忆和主动相关性/生成/复核；OpenMuse（CopilotKit/openmuse）主要参考持久执行、等待输入、产物与回执；OpenClaw参考定时/事件唤醒与静默，Hermes参考角色/上下文分层与真实完成依据。上述没有整套直接部署替代当前业务账本。

早期Postgres/pgvector、Graphiti、Mem0、FunASR/FastMCP属于候选方案；最终已走通实现以SQLite及现有处理图为主。不能把研究清单写成已经集成的功能墙，也不需要同时维护多套记忆权威。[第三方实际复用](heartball-third-party-components.md)
